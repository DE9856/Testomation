v0.5 — project brief
// project brief

Testomation

An autonomous software testing platform. It reads a codebase or app, decides what needs testing, writes the test cases itself, drives a real browser to run them, tells bugs apart from noise, and reports back — with minimal humans in the loop. It runs entirely on one laptop, on free and local tools.

00

Overview

Traditional test automation still needs a human to decide what to test and to write the script. Testomation moves both of those jobs to an AI agent: one that reasons about the application the way a QA engineer would, generates its own coverage, and only asks for a human when it isn't sure whether something is actually broken.

The goal isn't to replace scripted regression testing — it's to sit alongside it, filling the gap between "what we remembered to test" and "what the app can actually do."

Ground rules for v0.5

  • Free and local — everything runs on one laptop. No paid APIs or hosted services in the product.
  • Ollama at runtime — every model call the product makes goes to local models served by Ollama.
  • Claude for building — Claude (Claude Code) is the assistant used to build Testomation. It is not part of the product's runtime.
  • Playwright does the running — Playwright Test handles execution, parallel workers, retries, traces and screenshots. Testomation doesn't rebuild any of that.

What changed since v0.4

  • Tests are JSON specs, not code — the model fills a strict schema and one Playwright runner executes it. Nothing the model writes is ever executed. §05
  • Local models — the Claude API is replaced by Ollama with a small and a large local model tier plus a local embedding model. §10
  • No Temporal for now — a plain Python pipeline runner plus Playwright Test workers replace it on a single machine. §09
  • Budget is compute, not money — the per-run cap is LLM calls and wall-clock time, because VRAM, RAM and time are the scarce things now. §07
  • Claims in memory — human, rules and model verdicts about the same thing are stored side by side, so "human beats model" can actually be enforced. §06
  • Seeded-bug benchmark — a local target app with known bugs gives ground truth from day one. §11
  • App state reset — a seeded database is restored before each run, so results and flake signals mean something. §10

Cross-cutting layers

None of them adds a new pipeline step; they change how every existing step behaves.

  • Memory graph — a shared, persistent map of the app under test and everything Testomation has learned about it. Every agent reads it before acting and writes back after. §06
  • Cost & compute strategy — the LLM authors and interprets tests but never runs them. Deterministic tools go first; the model only sees what they couldn't settle. §07
  • Observability — self-hosted Langfuse traces every agent job, including the ones that never called a model, so tokens, latency, cache rate and analyzer accuracy are measurable. §08
  • Agent runtime — LangGraph runs the branching logic inside each reasoning agent (memory → rules → LLM → human review), while the pipeline runner and Playwright Test run the jobs around them. §09

They reinforce each other: memory is what makes most LLM calls unnecessary, LangGraph is what enforces "memory and rules before the model" in code, Langfuse is how you prove it's working, and the benchmark is how you know it's right.

01

The pipeline

01

Ingest

Pull in the target. For the MVP: a locally running web app (URL) and its repository. OpenAPI specs, design files and user stories come later.

02

Plan

An agent reasons about what should be tested — user flows, edge cases, boundary conditions, negative paths — and produces a structured coverage plan.

03

Generate

Each planned flow becomes a JSON test spec: a list of steps with role- or label-based targets and assertions, validated against a schema.

04

Execute

Playwright Test runs the specs through one generic spec runner. Traces, screenshots, DOM snapshots, console output and network traffic are captured.

05

Analyze & report

Evidence is compared against expected behaviour, classified and deduped, then written to a local report with repro steps and links to the evidence.

Every step, same loop: check the memory graph → try deterministic tools → call a local model only for what's still unanswered → write the result back to memory as a claim with provenance → log the whole job to Langfuse. In code, that loop is a small LangGraph graph per reasoning agent. Details in §06 and §09.
02

Feature catalog

Everything below is a candidate feature, grouped by where it sits in the system. core marks what an MVP needs to be useful at all; later marks what turns it from a working tool into a platform. Amber cards inside a core group are individually later.

Planning & test generation

core
  • Autonomous flow discoveryCrawls or reads the app and proposes the user flows worth testing, without being told what they are.
  • Natural-language test authoringA human types "test that guest checkout fails without an email" and gets a runnable spec.
  • Structured test specsTests are JSON specs run by one Playwright runner. The model fills a schema; it never writes executable code.
  • Edge-case & negative-path enumerationGenerates boundary values, invalid inputs, and error states alongside the happy path.
  • Coverage gap analysisFlags flows and routes that exist in the app but have no test touching them.
  • Requirement-to-test traceabilityLinks each generated test back to the user story or spec line that justified it.
  • Synthetic test data generationFaker references in specs produce realistic names, emails and files at run time, without real PII.
  • Test impact analysisGiven a code diff, works out which tests are affected and only reruns those. Starts from a static route → file map; runtime coverage refines it.

Memory & knowledge

core
  • Persistent app knowledge graphPages, flows, tests, bugs, commits and human decisions stored as linked nodes, so related things stay together across runs.
  • Memory-first lookupsAgents check what's already known before reasoning from scratch; answers get cached as graph facts.
  • Claims with provenanceEvery verdict records who asserted it (rules, LLM, human), how sure it is, and the Langfuse trace behind it. Conflicting claims coexist.
  • Change-aware invalidationA commit that touches a file marks dependent memory as stale until it's re-verified.

Execution

core
  • Parallel runsPlaywright Test workers fan specs out on the laptop — two workers while a model is loaded, more when it isn't.
  • App state resetThe target app's seeded database is restored before each run, and each test gets its own synthetic user so parallel workers don't collide.
  • Browser matrixChromium and Firefox on the laptop. WebKit through the official Playwright container, since Playwright doesn't officially support Fedora.
  • Responsive viewport testingReruns flows at phone, tablet, and desktop breakpoints.
  • Visual regression diffingPlaywright's built-in screenshot comparison against a baseline, with a highlighted diff.
  • Combined API + UI verificationCalls the backend directly to set up state, then verifies the frontend reflects it correctly.
  • Accessibility auditingRuns axe-core on every page visited and reports WCAG violations.
  • Auth & session handlingSaved Playwright storage state, so every test doesn't have to log in from scratch.
  • Third-party mockingRoute interception and HAR replay stub flaky or rate-limited services, so failures are the app's fault, not a dependency's.
  • Per-branch environmentsA throwaway local compose environment per branch, so tests run against that exact change.
  • Exploratory session recordingThe agent free-roams the app like a curious user, and every click, scroll, and state change is logged for later review — this is how it finds the bugs no one thought to write a test for.

Bug detection & analysis

core
  • Console & network error classificationSeparates real application errors from expected noise (ad blockers, analytics failures).
  • Severity & priority scoringRanks findings so a blocked checkout outranks a misaligned footer.
  • DeduplicationMatches a new failure against known bugs by error-signature hash first, local embeddings for borderline cases.
  • Confidence scoringConfidence comes from agreement across repeated model samples plus the rules signal, calibrated on the benchmark — not the model's self-report.
  • Flaky test detection & quarantineTracks pass/fail history per test and isolates ones that fail inconsistently. Runs under heavy machine load are excluded from the flake signal.
  • Multimodal visual bug detectionA small local vision model looks at suspected layout bugs that a pixel diff flagged but can't explain.
  • Root-cause suggestionCorrelates a failure's timing against recent commits and proposes which change likely caused it.
  • Regression clusteringGroups multiple failures that stem from the same underlying bug into one report instead of ten.

Human-in-the-loop & collaboration

core
  • Review queueA testomation review command to approve, reject, or edit anything the agent wasn't confident about. A local web UI comes later.
  • One-click test approvalGenerated specs start as drafts; a human promotes them into the regression suite.
  • Local run reportAn HTML/Markdown summary per run with repro steps and links to traces, next to Playwright's own HTML report.
  • Desktop notificationsA notification when a run finishes or a confirmed bug is found.
  • Inline annotationComment directly on a screenshot or trace step to explain context the agent missed.
  • GitHub Issues / Jira / SlackBugs become tickets and channel posts once the tool leaves the laptop.
  • Audit trailEvery decision the agent made — why it generated a test, why it flagged something — is logged and reviewable through claims and Langfuse traces.

Evaluating Testomation itself

core
  • Seeded-bug benchmarkA local target app with a catalogue of known bugs, each switchable on or off, gives ground truth.
  • Regression runs on every changeAny prompt, model or threshold change reruns the benchmark before it's kept.
  • Threshold calibrationConfidence gates are set from benchmark precision and recall instead of guessed, then refined with review-queue scores.

Reporting & analytics

later
  • Live dashboardCoverage, pass rate, flake rate, and open-bug count at a glance.
  • Trend graphs per releaseShows whether quality is improving or degrading release over release.
  • Per-module health scoringSurfaces which parts of the app are the most bug-prone or worst-covered.
  • Exportable reportsPDF or CSV summaries for stakeholders who don't live in the dashboard.
  • LLM usage trackingTokens, latency and calls per run and per agent via Langfuse. Local models cost no money, but they cost time.
  • Custom alerting rules"Notify me only if a payment flow breaks" instead of every flaky assertion.

Platform & integration

later
  • CI/CD pluginsNative steps for GitHub Actions, GitLab CI, and CircleCI so runs trigger on every PR.
  • Event-driven triggersRun on push, on deploy, nightly, or on demand — not just on a fixed schedule.
  • Public API / SDKProgrammatic control for teams who want to script Testomation into their own tooling.
  • Multi-project supportSeveral apps under test with isolated memory. The schema carries a project column from day one.
  • Production synthetic monitoringRuns a light version of the suite continuously against production to catch live incidents, not just pre-release bugs.
  • Plugin architectureLets teams add custom checks (brand guidelines, internal compliance rules) without forking the core.

Security & governance

later
  • Secrets managementSpecs reference credentials as $secret names; values are injected from the environment at run time and never stored.
  • PII redactionMasks sensitive data in screenshots and logs before they're stored or shared.
  • Role-based access controlControls who can approve tests, view evidence, or change production-monitoring schedules.
  • Sandboxed executionEvery browser session runs isolated, and because tests are specs rather than code, nothing a model writes is executed on the host.

// two languages, one boundary

Agents, memory, the pipeline and LangGraph are Python. The spec runner is TypeScript, because Playwright Test's TypeScript runner has the most features. They meet only through files: Python writes the run's specs as JSON, Playwright writes a JSON results file plus traces, and Python ingests both.

04

Components

Planner agent

Turns the app into a flow graph

Reads routes, components, API schema, or a live crawl of the app to build a map of user flows — "signup → verify email → onboarding," "add to cart → checkout → payment failure." The structural map comes from deterministic parsing, a state-graph crawler and Playwright aria snapshots; the local model's job is narrower — naming flows, ranking what matters, and inferring business rules a crawler can't see ("checkout should fail without an email").

Writes Page, Component, Element, Flow and ApiEndpoint nodes to memory, and only re-plans areas a diff actually touched.

Test generation agentchanged

Converts a flow into a JSON test spec

v0.4 left the test format open: scripted code, natural language resolved at runtime, or a hybrid. v0.5 settles it with a structured spec:

  • Spec, not code — the model fills a JSON schema (steps, role/label targets, assertions). Ollama's structured output constrains decoding to that schema, so small models can't produce invalid tests.
  • Deterministic execution — one generic Playwright runner executes every spec. Same determinism and speed as scripted tests, no generated code on the host.
  • Agents for exploration only — live, unscripted bug-hunting stays a separate executor mode (§09), as v0.4's hybrid recommended.

Before generating, it pulls targets that worked before and similar specs from memory to use as templates. Common patterns (login, form submit, CRUD) come from templates with no model call at all. Novel flows go through a generate → run → read error → repair loop with a hard retry cap. Repairs may change targets and add waits; changing or removing an assertion goes to review. See §05.

Executorchanged

Actually drives the browser

Two modes, kept separate rather than merged into one agent:

  • Playwright Test + spec runner — runs approved specs with workers and retries. Fast and repeatable; the right choice for regression gates.
  • Exploratory agent loop — aria snapshot → local model picks the next action → execute → repeat, with invariant checks on every state. A small vision model is optional. Slower, but it finds the bugs a spec wasn't written to look for.

Evidence comes from Playwright itself: the trace file (screenshots, DOM snapshots, console, network), failure screenshots and video, axe results, and Chromium JS coverage per test. Evidence is written to data/evidence/<run>/; coverage becomes the touches edges that power test impact analysis.

Analyzer agent

Decides what's actually a bug

Reasons over the evidence bundle rather than a single assertion. Signal sources include failed assertions, console exceptions, 4xx/5xx network responses, visual regressions, dead-end navigation states, and accessibility violations.

Runs as a rules engine first — known noise signatures, status codes, axe-core, screenshot diffs, flake history — and escalates to the small local model only for failures nothing else could classify. The model is sampled three times; agreement, not self-reported certainty, sets confidence. This is the first agent built as a LangGraph graph (§09).

Reporter

Closes the loop with humans

Writes a local HTML/Markdown report per run — confirmed bugs, repro steps, links to traces and screenshots — next to Playwright's HTML report, and sends a desktop notification. GitHub Issues, Jira and Slack come once the tool leaves the laptop.

Review queuenew

Where uncertain decisions wait for a human

An interrupted LangGraph thread is a review item. A small review_item table lists them, because checkpoints aren't built for listing. testomation review shows each item with its evidence, opens the trace with npx playwright show-trace, and resumes the graph with the decision. Decisions become human claims in memory and scores in Langfuse.

Pipeline runnerchanged

Keeps everything coordinated

Replaces the v0.4 orchestrator on a single machine. testomation run executes a fixed sequence of stages, records each stage's state in Postgres so a crashed run resumes from the last completed stage, enforces the per-run compute budget, and uses the memory graph to decide which specs a diff needs. Fan-out and retries are Playwright Test's job; reasoning inside each agent is LangGraph's. Temporal returns only if Testomation spreads across machines.

Agent runtime (LangGraph)

Runs the decision loop inside each reasoning agent

Each reasoning agent is a small graph: plain-Python nodes for memory and rules, one node that calls a local model, conditional edges on confidence, and a pause point for human review. See §09.

Memory graph

Shared knowledge every agent reads and writes

Not an agent — a store. It holds the relationships between pages, flows, specs, bugs, commits and human decisions, plus the claims each source made about them. See §06.

Observability (Langfuse)

Records what every agent did and how long it took

Self-hosted. Wraps each agent job in a trace. Model calls appear as generations with tokens and latency; deterministic steps appear as spans, so skipped model calls are visible too. See §08.

05

Test spec

A test is data, not code. The model fills a JSON schema; one Playwright runner interprets it. This suits small local models, which fill a fixed schema far more reliably than they write free-form code. It also means generated tests are easy to diff, dedupe, store in the graph and repair — and nothing a model writes is executed on the laptop.

{
  "spec_version": 1,
  "id": "checkout.guest.no-email",
  "flow": "guest-checkout",
  "requirement": "REQ-142",
  "steps": [
    { "action": "goto",   "url": "/cart" },
    { "action": "click",  "target": { "role": "button", "name": "Checkout" } },
    { "action": "fill",   "target": { "label": "Name" },  "value": { "$faker": "person.fullName" } },
    { "action": "fill",   "target": { "label": "Email" }, "value": "" },
    { "action": "click",  "target": { "role": "button", "name": "Place order" } },
    { "action": "expect", "target": { "role": "alert" },  "assert": "hasText", "value": "Email is required" }
  ]
}
// step vocabulary
ActionFieldsNotes
gotourlRelative to the target's base URL
click · hovertarget
fill · selecttarget, valueValue may be a literal or a reference
check · unchecktarget
presskey, optional target
uploadtarget, fileFile is a $fixture reference
wait_fortarget, statevisible · hidden
expecttarget or page, assert, valuevisible · hidden · hasText · hasValue · count · url · ariaSnapshot
apimethod, path, body, optional expectBackend setup and verification through Playwright's request context
viewportpresetphone · tablet · desktop
// targets and values
  • Targets — one of testid, role + name, label, placeholder, text, in that order of preference. CSS and XPath aren't in the schema.
  • $faker — synthetic data generated at run time ({"$faker": "internet.email", "as": "email"}); {"$var": "email"} reuses it later in the spec.
  • $secret — a credential name, resolved from the environment at run time and never stored.
  • $fixture — a file from the project's fixtures folder.
// runner, lifecycle, repair
  • Spec runner — one Playwright test file registers a test() per spec and wraps each step in test.step(), so steps show up by name in traces and reports. Fixtures add axe checks, coverage and an aria snapshot on failure.
  • Exporter (later) — turns a spec into a readable .spec.ts for anyone who wants to own a test outside Testomation.
  • Lifecycle — draft → approved → quarantined → retired, stored on the TestCase node. Only approved specs run in regression.
  • Repair — a failing draft goes back to the large model with the failing step, the error and the aria snapshot, capped at three attempts. Repairs may change targets or add waits. Changing or removing an expect needs review, because the failure might be a real bug.
  • Approved specs never self-heal — any change to an approved spec is a drift signal for the analyzer and a review item.
06

Memory graph

The memory graph is Testomation's long-term knowledge about the app under test: what exists, what's been tested, what broke, why, and what humans decided. It keeps useful things connected — a bug is linked to the component it affects, the commit that likely caused it, the test that found it and the evidence that proves it — so any agent can follow those links instead of re-deriving them.

// what it stores
  • App structurePage, Component, Element, ApiEndpoint, SourceFile
  • Test knowledgeFlow, TestCase (holds the spec and its status), Run, Evidence (a path in the evidence folder)
  • FindingsBug, NoiseSignature (errors known to be harmless), Requirement
  • HistoryCommit, HumanDecision (approve / reject / annotate)

The edges are what make it useful:

  • Flow —visits→ Page —calls→ ApiEndpoint
  • Page —renders→ Component —contains→ Element
  • TestCase —covers→ Flow · TestCase —justified_by→ Requirement
  • TestCase —touches→ SourceFile (static map first, then coverage)
  • Commit —changes→ SourceFile new
  • Bug —found_in→ Run · Bug —affects→ Component · Bug —likely_caused_by→ Commit
  • Evidence —matches→ NoiseSignature
  • HumanDecision —confirmed | rejected→ Bug / TestCase
// how it plugs into the pipeline

Memory doesn't add a step — it wraps every existing one in the same five-part loop:

a

Look up

Before acting, the agent queries the graph. Is this error a known noise signature? Is there a working target for this element? Has this flow been planned, and has nothing it touches changed since?

b

Try deterministic tools

If memory doesn't answer it, rules, parsers, crawlers and diffing get the next shot (§07).

c

Escalate to a local model

Only what's still unanswered reaches a model — with the relevant neighbourhood of the graph as context, rather than the whole app.

d

Write back

The answer becomes a claim on a node, stamped with its source (rules / LLM / human), a confidence level, and the Langfuse trace ID. Next time, step (a) answers it for free.

e

Invalidate on change

When a commit lands, its changes edges lead to files, which are followed through touches and renders; every dependent node and claim is marked stale until re-verified.

// what each agent reads and writes
AgentReads before actingWrites after
PlannerExisting flows, pages with no covering test, bug-prone componentsPage, Component, Element, Flow, ApiEndpoint
Test genTargets that worked, similar specs to template from, test data that passed a form's validationTestCase nodes (spec + status) linked to flows and requirements
ExecutorStored auth state, slow endpoints to mockRun, Evidence paths, touches edges
AnalyzerNoise signatures, past bugs on the same component, recent commits touching itBug, NoiseSignature, verdict claims, dedup links
ReporterAffected requirements, owning moduleReport paths (ticket IDs later) on Bug nodes
Pipeline runnerDiff → changes → touches → affected specsCommit nodes, stale flags
Review queueLow-confidence claims awaiting a humanHuman claims, HumanDecision nodes (also sent to Langfuse as scores)
// features that become graph queries
  • Coverage gap analysis — pages with no incoming covers path.
  • Test impact analysis — commit → changes → files → touches → tests to rerun.
  • Traceability — test → justified_by → requirement.
  • Dedup & regression clustering — failures sharing a component and an error signature.
  • Root-cause suggestion — bug → component → recent commits touching it.
  • Per-module health — bug and coverage counts rolled up per component.
// trust rules
  • Provenance on everything — nodes, edges and claims all record their source, confidence and the trace ID that produced them.
  • Human beats model — for any node and field, the newest non-stale human claim wins; otherwise the highest-confidence non-stale claim. Losing claims are kept, not overwritten.
  • No silent suppression — an LLM-inferred NoiseSignature never auto-hides a failure until a human confirms it.
  • Stale until proven — stale nodes and claims can inform an agent but can't short-circuit a decision, even human ones.
// storage

Postgres with pgvector for fuzzy matching ("is this error similar to a known one?"). Traversals are mostly one to three hops, which recursive CTEs handle fine; a dedicated graph database is only worth it if they get deep or slow. Embedding size follows the local embedding model — 768 for the current candidate.

-- nodes: the things the system knows about
CREATE TABLE mem_node (
  id          uuid PRIMARY KEY,
  project     text NOT NULL DEFAULT 'default',
  kind        text NOT NULL,        -- 'Page', 'Bug', 'TestCase', ...
  key         text NOT NULL,        -- natural key, e.g. route or error hash
  props       jsonb NOT NULL DEFAULT '{}',
  embedding   vector(768),          -- optional; size of the local embed model
  source      text NOT NULL,        -- who created it: 'rules' | 'llm' | 'human'
  trace_id    text,                 -- Langfuse trace that created it
  stale       boolean NOT NULL DEFAULT false,
  updated_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (project, kind, key)
);

-- edges: how those things relate, with the same provenance
CREATE TABLE mem_edge (
  src         uuid REFERENCES mem_node(id),
  rel         text NOT NULL,        -- 'covers', 'touches', 'changes', ...
  dst         uuid REFERENCES mem_node(id),
  props       jsonb NOT NULL DEFAULT '{}',
  source      text NOT NULL,
  confidence  real NOT NULL DEFAULT 1.0,
  trace_id    text,
  stale       boolean NOT NULL DEFAULT false,
  updated_at  timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (src, rel, dst)
);

-- claims: what each source asserts about a node; several can coexist
CREATE TABLE mem_claim (
  id          uuid PRIMARY KEY,
  node_id     uuid NOT NULL REFERENCES mem_node(id),
  field       text NOT NULL,        -- 'verdict', 'is_noise', 'severity', ...
  value       jsonb NOT NULL,
  source      text NOT NULL,        -- 'rules' | 'llm' | 'human'
  confidence  real NOT NULL,
  trace_id    text,
  stale       boolean NOT NULL DEFAULT false,
  created_at  timestamptz NOT NULL DEFAULT now()
);

A mem_fact view applies the "human beats model" rule to claims, so agents read one resolved value per node and field.

07

Cost & compute strategy

The rule: the LLM writes and interprets tests; it never runs them. A spec generated once and run a thousand times by Playwright costs one generation. Model work then scales with how much the app changes, not with how often it's tested.

On a laptop with local models, the cost isn't money — it's VRAM, RAM and time. The rule protects those instead: every model call avoided is seconds saved and a browser worker that doesn't have to wait.

// deterministic first, LLM for the residue
StageDeterministic firstModel only for
PlanRouter / sitemap / OpenAPI parsing; state-graph crawler; aria snapshotsNaming and ranking flows; inferring business rules
GenerateSpec templates for common patterns; boundary values from HTML attributes; schema-driven API specs; Faker referencesNovel multi-step flows (as specs, never code)
ExecutePlaywright Test running specs with role / test-id targetsNothing
AnalyzeAssertions, status codes, console allowlist, axe-core, screenshot diff, flake historyFailures matching no known signature
DedupeHash of normalised error signatureBorderline matches (local embeddings first)
ReportTemplated reports and notificationsOptional summary on filed bugs
ImpactStatic route → file map, then coverage, via the memory graphNothing
// making the remaining calls cheap
  • Memory before model — the graph is the cache; a question answered once isn't asked again.
  • Change-triggered — re-plan and regenerate only what a diff touched.
  • Model tiers — a ~4B model that fits entirely on the GPU for classification, dedup and naming; a ~7–8B model with partial CPU offload for spec generation, planning and repair.
  • Structured output — JSON-schema-constrained decoding means no calls are wasted on output that can't be parsed.
  • Text over pixels — send the aria snapshot or a trimmed DOM; screenshots only for suspected visual bugs.
  • Group work by model — 4 GB of VRAM holds one model at a time. Batch all small-model work, then all large-model work, and keep the model loaded for the whole batch to avoid reload cost.
  • Overnight batches — planning and generation for areas a PR didn't touch can run while the laptop is idle.
  • Hard per-run budget — a cap on model calls and model wall-clock time per run. Once it's spent, remaining items go to the review queue.
// exploratory testing without a vision loop

Before reaching for any agent, run monkey/fuzz interaction and coverage-guided crawling, checking invariants on every state reached: no console errors, no 5xx responses, no axe violations, nothing overflowing the viewport. The exploratory agent then works on aria snapshots with a text model; a small vision model is an optional, budgeted deep pass on high-value flows.

Observability with Langfuse

Langfuse is the record of what each agent did, how long it took, and whether it was right. It is self-hosted on the laptop with its Docker Compose setup. Its trace model maps cleanly onto Testomation:

// instrumentation sketch
from langfuse import observe, get_client, propagate_attributes
from langfuse.openai import OpenAI     # drop-in client: every call → a generation

llm = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")  # local Ollama
langfuse = get_client()                # reads LANGFUSE_* env vars (self-hosted)

@observe(name="analyzer.triage", capture_input=False)  # no raw DOM / screenshots
def triage_failure(failure, run_id):
    with propagate_attributes(session_id=run_id, tags=["agent:analyzer"]):
        hit = memory.lookup_noise(failure.signature)       # (a) memory
        langfuse.update_current_span(metadata={"memory_hit": hit is not None})
        if hit and hit.source == "human" and not hit.stale:
            return hit.verdict

        verdict = rules_engine.classify(failure)           # (b) deterministic
        if verdict.confident:
            memory.claim(verdict, source="rules")
            return verdict

        verdict = llm_classify(llm, failure, tier="small", samples=3)  # (c) model
        memory.claim(verdict, source="llm",                # (d) write back
                     trace_id=langfuse.get_current_trace_id())
        return verdict

Call langfuse.flush() before a short-lived worker or CLI command exits.

// how it ties to memory and compute
  • Graph ↔ trace links — every model-created node and claim stores its trace ID, so any bug or spec can be traced back to the exact reasoning and prompt version that produced it.
  • Cache rate — a memory_hit flag on every span shows the share of decisions memory answered, which should climb as the graph matures.
  • Budget enforcement — the pipeline runner counts model calls and model time per session and stops escalating once a run's budget is used.
  • Analyzer accuracy — review-queue decisions are written back as scores, giving real precision numbers alongside the benchmark.
  • LangGraph tracing — Langfuse's LangChain callback handler traces LangGraph runs, so each graph node appears as its own span without extra instrumentation.
  • Prompt management & datasets — prompts are versioned in Langfuse; benchmark and hard triage cases become datasets to rerun on every prompt change or model swap.
Local models have no price. Langfuse won't show a cost for them, so track tokens, latency and call counts instead — those are the numbers that matter on a laptop. Keep capture_input=False on anything that sees page content, and log evidence paths rather than raw payloads.

Deciding, inside one agent, whether memory answered a question, whether the rules engine is sure, and whether to ask a human is reasoning control flow. On one laptop, the job side doesn't need Temporal: a plain pipeline runner and Playwright Test on the outside, LangGraph on the inside.

// sketch
from typing import TypedDict, Optional
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.postgres import PostgresSaver
from langfuse.langchain import CallbackHandler

class Triage(TypedDict):
    failure: dict
    verdict: Optional[dict]
    confidence: float
    source: str                     # 'memory' | 'rules' | 'llm' | 'human'

def memory_lookup(s): ...           # plain Python; only fresh human claims count as a hit
def rules_engine(s):  ...           # plain Python, no model
def llm_classify(s):  ...           # the ONLY node that calls a model (local, small tier);
                                    # 3 samples, confidence = agreement;
                                    # confidence=0 if the run's compute budget is spent
def review(s):
    decision = interrupt({"failure_id": s["failure"]["id"]})   # graph pauses here
    return {"verdict": decision, "source": "human", "confidence": 1.0}
def write_back(s):    ...           # memory.claim(verdict, source=s["source"], ...)

g = StateGraph(Triage)
for name, fn in [("memory", memory_lookup), ("rules", rules_engine),
                 ("llm", llm_classify), ("review", review), ("write", write_back)]:
    g.add_node(name, fn)

g.add_edge(START, "memory")
g.add_conditional_edges("memory", lambda s: "write" if s["source"] == "human" else "rules")
g.add_conditional_edges("rules",  lambda s: "write" if s["confidence"] >= 0.9 else "llm")
g.add_conditional_edges("llm",    lambda s: "write" if s["confidence"] >= 0.8 else "review")
g.add_edge("review", "write")
g.add_edge("write", END)

analyzer = g.compile(checkpointer=PostgresSaver(conn))   # same Postgres as memory

# inside the pipeline's triage stage
cfg = {"configurable": {"thread_id": f"triage-{failure['id']}"},
       "callbacks": [CallbackHandler()]}                  # every node -> Langfuse span
analyzer.invoke({"failure": failure}, config=cfg)

# later, when a reviewer decides in `testomation review`
analyzer.invoke(Command(resume=reviewer_decision), config=cfg)

The 0.9 and 0.8 thresholds are placeholders until the benchmark calibrates them (§11).

// what this buys
  • Compute rules enforced in code — the order memory → rules → model is the graph's shape, not a convention each agent has to remember.
  • Review queue for free — an interrupted graph is a review-queue item. The reviewer's decision resumes it, the result is written to memory as a human claim, and it's sent to Langfuse as a score.
  • Crash-safe exploration — checkpoints in the same Postgres as the memory graph mean a long exploratory session resumes where it stopped.
  • Visible paths — with the Langfuse handler attached, every node is a span, so you can see how many failures took the free path versus the model path.
When Temporal comes back. If Testomation spreads across several machines, needs many concurrent runs, or must survive restarts in the middle of a stage, Temporal replaces the pipeline runner — stage for stage — and LangGraph stays exactly where it is.

Evaluation

Without ground truth there's no way to tell whether a new prompt, threshold or model made Testomation better or worse. Review-queue scores help, but they only exist once humans have reviewed things. A seeded-bug benchmark works from day one.

// the benchmark
  • Target app — one small but realistic web app (auth, forms, CRUD, lists) run locally with a seeded database. A RealWorld ("Conduit") implementation is a good candidate.
  • Hand-planted bugs — about twenty across categories: broken flows, missing validation, 5xx responses, console errors, layout breaks, accessibility violations, an intentionally flaky element, and harmless noise that must not be reported.
  • Mutation bugs — a mutation-testing tool such as Stryker adds many small automatic bugs to the app's code.
  • Toggles — every bug can be switched on or off, so the same app runs clean or bugged.
// what gets measured
MetricQuestion it answers
Bug recallOf the seeded bugs, how many were reported?
False-positive rateHow many reports on the clean app, or for planted noise?
Noise precisionWhen something was called noise, was it really noise?
Review-queue rateHow much work was pushed to a human?
Spec success rateShare of generated specs that are valid and pass on the clean app within the repair cap
Model calls & time per runWhat did it cost in compute?
Memory hit rateHow much did memory answer on a second run?
// how it's used
  • testomation bench — runs the clean and bugged variants and scores them; results go to bench/results/ and Langfuse dataset runs.
  • Gate every change — any prompt, model or threshold change reruns the benchmark before it's kept.
  • Calibrate thresholds — the analyzer's confidence gates are set from the benchmark's precision and recall, then refined with review-queue scores.
  • Pick models — the model-tier candidates in §10 compete on the benchmark, not on reputation.
  • Hold some bugs out — a held-out set of seeded bugs that prompts are never tuned against shows whether changes really improve detection or just fit the benchmark.

Design risks worth building around

Self-healing can hide real bugs

A tool that quietly swaps in a new target when one breaks and re-runs isn't the same as understanding why it broke. If a button moved because a layout regressed, silently "healing" the test buries the exact bug it existed to catch. Approved specs never self-heal: any change is a drift signal and a review item, and repairs to drafts can't touch assertions.

Agent runs are slow and non-deterministic

Great for exploratory bug-hunting, bad for a regression gate that needs to be fast and repeatable. Keep spec execution and agentic exploration as two distinct modes rather than asking one agent to do both jobs well.

Small local models are weaker

A 4–8B model will misjudge things a frontier model wouldn't. Keep their jobs narrow, make them fill schemas instead of writing code, put deterministic tools first, derive confidence from agreement rather than self-report, and gate every prompt or model change on the benchmark.

Memory can learn the wrong lesson

If the Analyzer once wrongly decides a 500 error is noise and saves that as a signature, it will ignore that bug on every future run. It's the same failure mode as self-healing, made permanent. LLM-inferred suppressions must stay in the review queue until a human confirms them.

Stale memory looks like fresh knowledge

A target or flow that was correct last month may not be today. Invalidation on every commit, plus treating stale nodes and claims as hints rather than answers, keeps old facts from short-circuiting new decisions.

Shared app state makes tests lie

If tests share accounts or leftover data, failures depend on run order and every flake signal is noise. Restore the seeded database before each run and give each test its own synthetic user.

The laptop becomes the bottleneck

Langfuse, a loaded model, the target app and several browsers compete for 16 GB of RAM and 4 GB of VRAM. Swapping makes tests time out and look flaky. Cap workers while a model is loaded, keep generation and execution apart, and record machine load with each run.

A compute budget can quietly cost coverage

A tight budget that routes everything to the review queue just moves the work to humans. Watch review-queue size next to model calls and time; if one drops while the other climbs, the budget is set wrong.

Two orchestrators can blur into one

If LangGraph starts handling parallel runs and retries, or the pipeline runner starts encoding agent decisions, you get two half-overlapping systems and state that lives in both. Keep the line sharp: the runner and Playwright own jobs; LangGraph owns decisions within one item.

Build order

PHASE 0

Set the stage

Compose stack (Postgres + pgvector, Langfuse), native Ollama with candidate models pulled, a target app with a seeded database and reset, and the seeded-bug catalogue with toggles. testomation bench can already score a hand-written suite.

PHASE 1

Prove the plumbing

The spec schema and the Playwright spec runner, running hand-written specs and capturing evidence into the local folder. Create the memory schema (nodes, edges, claims) now: specs, runs and evidence paths are its first nodes, and a static route → file map gives the first touches edges. Trace pipeline stages in Langfuse from day one. No model calls yet.

PHASE 2

Tell bugs from noise — rules only

The analyzer's deterministic half: assertions, status codes, console allowlist, axe, screenshot diffs, flake history, dedup by error hash. It writes rule claims, noise signatures and a local report. Its benchmark scores become the baseline every model-based feature has to beat.

PHASE 3

Generate specs from plain English

Test gen with the large local model: described flow → JSON spec under constrained decoding, a capped repair loop that can't touch assertions, and drafts promoted with testomation approve. Generated specs land in memory linked to the flows they cover. The repair loop stays plain code for now.

PHASE 4

Plan the coverage

A planner built as crawler + parser + aria snapshots first, with the small model naming and ranking flows. It populates Page, Component, Element, Flow and ApiEndpoint nodes, and re-plans only what a diff touches.

PHASE 5

Put the model in the loop

The analyzer becomes the first LangGraph graph: memory → rules → small model ×3 → confidence gate → interrupt(). testomation review resumes paused graphs; decisions become human claims and Langfuse scores. Thresholds are calibrated on the benchmark. Move the test-gen repair loop onto LangGraph once the pattern is proven.

PHASE 6

Go exploratory

Fuzzing and coverage-guided crawling with invariant checks first, then a text-based exploratory agent over aria snapshots (a LangGraph loop that stops when budget or new states run out), an optional small vision model, plus flaky-test quarantine and visual baselines — the trio that turns a test runner into something that finds bugs on its own.

LATER

Platformize

CI/CD plugins, dashboard and trend analytics (read from the memory graph and Langfuse), GitHub Issues / Jira / Slack, production synthetic monitoring, RBAC, multi-project UI, the plugin architecture, WebKit through the Playwright container — and Temporal, if Testomation ever outgrows one machine.
