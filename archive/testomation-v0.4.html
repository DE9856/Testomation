v0.4 — project brief
// project brief

Testomation

An autonomous software testing platform. It reads a codebase or app, decides what needs testing, writes the test cases itself, drives a real browser to run them, tells bugs apart from noise, and reports back — with minimal humans in the loop.

00

Overview

Traditional test automation still needs a human to decide what to test and to write the script. Testomation moves both of those jobs to an AI agent: one that reasons about the application the way a QA engineer would, generates its own coverage, and only asks for a human when it isn't sure whether something is actually broken.

The goal isn't to replace scripted regression testing — it's to sit alongside it, filling the gap between "what we remembered to test" and "what the app can actually do."

What changed since v0.2

Four cross-cutting layers now sit underneath the five agents. None of them adds a new pipeline step; they change how every existing step behaves.

  • Memory graph — a shared, persistent map of the app under test and everything Testomation has learned about it. Every agent reads it before acting and writes back after. §05
  • Cost strategy — the LLM authors and interprets tests but never runs them. Deterministic tools go first; the model only sees what they couldn't settle. §06
  • Observability — Langfuse traces every agent job, including the ones that never called a model, so cost, cache rate and analyzer accuracy are measurable. §07
  • Agent runtime — LangGraph runs the branching logic inside each reasoning agent (memory → rules → LLM → human review), while Temporal runs the jobs around them. §08

They reinforce each other: memory is what makes most LLM calls unnecessary, LangGraph is what enforces "memory and rules before the model" in code, and Langfuse is how you prove it's working.

01

The pipeline

01

Ingest

Pull in the target: repo, live URL, OpenAPI spec, design files, or user stories. This is the raw material the Planner works from.

02

Plan

An agent reasons about what should be tested — user flows, edge cases, boundary conditions, negative paths — and produces a structured coverage plan.

03

Generate

Each planned flow becomes an executable test: Playwright code, plain-language steps for an agent to run live, or both.

04

Execute

A browser actually runs the flow. Screenshots, DOM state, console output, and network traffic are captured at every step.

05

Analyze & report

Evidence is compared against expected behavior, classified and deduped, then pushed out as a readable bug report with repro steps attached.

Every step, same loop: check the memory graph → try deterministic tools → call the LLM only for what's still unanswered → write the result back to memory with its provenance → log the whole job to Langfuse. In code, that loop is a small LangGraph graph per agent. Details in §05 and §08.
02

Feature catalog

Everything below is a candidate feature, grouped by where it sits in the system. core marks what an MVP needs to be useful at all; later marks what turns it from a working tool into a platform.

Planning & test generation

core
  • Autonomous flow discoveryCrawls or reads the app and proposes the user flows worth testing, without being told what they are.
  • Natural-language test authoringA human can type "test that guest checkout fails without an email" and get a runnable test.
  • Edge-case & negative-path enumerationGenerates boundary values, invalid inputs, and error states alongside the happy path.
  • Coverage gap analysisFlags flows and routes that exist in the app but have no test touching them.
  • Requirement-to-test traceabilityLinks each generated test back to the user story or spec line that justified it.
  • Synthetic test data generationProduces realistic names, emails, payment data, and file uploads for forms, without using real PII.
  • Test impact analysisGiven a code diff, works out which existing tests are actually affected and only reruns those — the difference between a 40-minute suite and a 3-minute one on every PR.

Memory & knowledge

core
  • Persistent app knowledge graphPages, flows, tests, bugs, commits and human decisions stored as linked nodes, so related things stay together across runs.
  • Memory-first lookupsAgents check what's already known before reasoning from scratch; answers get cached as graph facts.
  • Provenance & confidenceEvery fact records who created it (rules, LLM, human), how sure it is, and the Langfuse trace behind it.
  • Change-aware invalidationA commit that touches a file marks dependent memory as stale until it's re-verified.

Execution

core
  • Parallel/distributed runsFans tests out across a browser pool so a full suite runs in minutes, not hours.
  • Cross-browser matrixSame test, run against Chromium, Firefox, and WebKit to catch engine-specific bugs.
  • Responsive & mobile-web viewport testingReruns flows at phone, tablet, and desktop breakpoints.
  • Visual regression diffingPixel or perceptual comparison against a baseline screenshot, with a highlighted diff.
  • Combined API + UI verificationCalls the backend directly to set up state, then verifies the frontend reflects it correctly.
  • Accessibility auditingRuns axe-core (or similar) on every page visited and reports WCAG violations.
  • Auth & session handlingStores and reuses login sessions so every test doesn't have to re-authenticate from scratch.
  • Third-party mockingStubs flaky or rate-limited external services (payments, email, maps) so failures are the app's fault, not a dependency's.
  • Ephemeral preview environmentsSpins up a throwaway environment per pull request so tests run against that exact change, not a shared staging server.
  • Exploratory session recordingThe agent free-roams the app like a curious user, and every click, scroll, and state change is logged for later review — this is how it finds the bugs no one thought to write a test for.

Bug detection & analysis

core
  • Multimodal visual bug detectionA vision model spots overlapping elements, cropped text, and broken layouts a pixel-diff alone would miss.
  • Console & network error classificationSeparates real application errors from expected noise (ad blockers, analytics failures).
  • Severity & priority scoringRanks findings so a blocked checkout outranks a misaligned footer.
  • DeduplicationMatches a new failure against existing open tickets instead of filing a duplicate.
  • Confidence scoringEvery finding carries a confidence level; low-confidence ones route to a human review queue instead of auto-filing.
  • Flaky test detection & quarantineTracks pass/fail history per test and automatically isolates ones that fail inconsistently, rather than letting them erode trust in the suite.
  • Root-cause suggestionCorrelates a failure's timing against recent commits and proposes which change likely caused it.
  • Regression clusteringGroups multiple failures that stem from the same underlying bug into one report instead of ten.

Human-in-the-loop & collaboration

core
  • Review queueA single place to approve, reject, or edit anything the agent wasn't confident about.
  • One-click test approvalGenerated tests start in draft; a human promotes them into the regression suite.
  • Inline annotationComment directly on a screenshot or trace step to explain context the agent missed.
  • Jira / Linear / GitHub Issues syncBugs become tickets automatically, with status synced both ways.
  • Slack / Teams notificationsFailures post to the right channel with the evidence bundle attached, not just a red X.
  • Audit trailEvery decision the agent made — why it generated a test, why it flagged something — is logged and reviewable.

Reporting & analytics

later
  • Live dashboardCoverage, pass rate, flake rate, and open-bug count at a glance.
  • Trend graphs per releaseShows whether quality is improving or degrading release over release.
  • Per-module health scoringSurfaces which parts of the app are the most bug-prone or worst-covered.
  • Exportable reportsPDF or CSV summaries for stakeholders who don't live in the dashboard.
  • LLM cost & compute trackingShows what each test run and each agent actually costs, via Langfuse, so spend stays visible as usage scales.
  • Custom alerting rules"Notify me only if a payment flow breaks" instead of every flaky assertion.

Platform & integration

later
  • CI/CD pluginsNative steps for GitHub Actions, GitLab CI, and CircleCI so runs trigger on every PR.
  • Event-driven triggersRun on push, on deploy, nightly, or on demand — not just on a fixed schedule.
  • Public API / SDKProgrammatic control for teams who want to script Testomation into their own tooling.
  • Multi-project / multi-tenant supportOne instance serving several teams or products with isolated data.
  • Production synthetic monitoringRuns a light version of the suite continuously against production to catch live incidents, not just pre-release bugs.
  • Plugin architectureLets teams add custom checks (brand guidelines, internal compliance rules) without forking the core.

Security & governance

later
  • Secrets managementTest credentials are injected at run time, never stored in a generated script.
  • PII redactionMasks sensitive data in screenshots and logs before they're stored or shared.
  • Role-based access controlControls who can approve tests, view evidence, or change production-monitoring schedules.
  • Sandboxed executionEvery browser session runs isolated, so one test can't affect another's state or leak data across tenants.

Five agents, one orchestrator, one shared memory. Test cases now live in the graph as TestCase nodes; the executor still runs them on a Playwright browser pool. The orchestrator runs as Temporal workflows; agents that branch run as LangGraph graphs inside those workflows' activities.

04

Components

Planner agent

Turns the app into a flow graph

Reads routes, components, API schema, or a live crawl of the app to build a map of user flows — "signup → verify email → onboarding," "add to cart → checkout → payment failure." The structural map comes from deterministic parsing and a state-graph crawler; the LLM's job is narrower — naming flows, ranking what matters, and inferring business rules a crawler can't see ("checkout should fail without an email").

Writes Page, Flow and ApiEndpoint nodes to memory, and only re-plans areas a diff actually touched.

Test generation agent

Converts a flow into something executable

This is the biggest architectural fork in the whole system — how a "test" is represented:

  • Scripted output — the LLM writes Playwright/Cypress code. Deterministic, fast, version-controllable. Brittle if the UI changes and the model guessed a selector.
  • Natural-language, resolved at runtime — steps like "click the login button," resolved live by an agent using vision or the DOM instead of a hardcoded selector. More resilient to UI drift, slower and less deterministic per run.
  • Hybrid (recommended) — scripted tests for the regression suite that runs in CI; an agent held in reserve for exploratory coverage and unscripted bug-hunting.

Before generating, it pulls locators that worked before and similar existing tests from memory to use as templates. Common patterns (login, form submit, CRUD) come from templates with no LLM call at all. Novel flows go through a generate → run → read error → repair loop with a hard retry cap.

Executor

Actually drives the browser

Two modes, kept separate rather than merged into one agent:

  • Playwright/Puppeteer running generated code directly — fast, parallelizable, the right choice for CI gates.
  • CDP + vision agent loop — screenshot → model decides the next action → execute → repeat. Slower and more expensive, but this is what finds the bug a script wasn't written to look for.

Every run captures screenshots, DOM snapshots, console errors, network requests, and a trace recording — evidence, not just a pass/fail flag. Code coverage per test is recorded too, which becomes the touches edges that power test impact analysis.

Analyzer agent

Decides what's actually a bug

Reasons over the evidence bundle rather than a single assertion. Signal sources include failed assertions, console exceptions, 4xx/5xx network responses, visual regressions, dead-end navigation states, and accessibility violations. A multimodal model is genuinely useful here — it can look at two screenshots and explain "this button overlaps this text" in a way a pixel-diff alone can't.

Runs as a rules engine first — known noise signatures, status codes, axe-core, perceptual diffs, flake history — and escalates to the model only for failures nothing else could classify. This is the first agent built as a LangGraph graph (§08).

Reporter

Closes the loop with humans

Structured output routes to Jira/Linear as a ticket, Slack as a notification, and a dashboard tracking coverage, flake rate, and bug counts over time — always with the evidence bundle attached so nobody has to re-run anything to triage.

Orchestrator

Keeps everything coordinated

A job/state layer — Temporal, or a simpler Redis/Celery queue — handling retries, parallel browser sessions, LLM rate-limiting, and checkpointing so a crash mid-exploration doesn't lose progress. It also enforces a per-run LLM budget and uses the memory graph to decide which tests a given diff actually needs. It owns the fleet; the reasoning inside each agent belongs to LangGraph.

Agent runtime (LangGraph)new

Runs the decision loop inside each reasoning agent

Each reasoning agent is a small graph: plain-Python nodes for memory and rules, one node that calls the model, conditional edges on confidence, and a pause point for human review. See §08.

Memory graphnew

Shared knowledge every agent reads and writes

Not an agent — a store. It replaces the old standalone test-case store and holds the relationships between pages, flows, tests, bugs, commits and human decisions. See §05.

Observability (Langfuse)new

Records what every agent did and what it cost

Wraps each agent job in a trace. LLM calls appear as generations with tokens and cost; deterministic steps appear as spans, so skipped LLM calls are visible too. See §07.

05

Memory graph

The memory graph is Testomation's long-term knowledge about the app under test: what exists, what's been tested, what broke, why, and what humans decided. It keeps useful things connected — a bug is linked to the component it affects, the commit that likely caused it, the test that found it and the evidence that proves it — so any agent can follow those links instead of re-deriving them.

// what it stores
  • App structurePage, Component, Element, ApiEndpoint, SourceFile
  • Test knowledgeFlow, TestCase, Run, Evidence (a pointer into blob storage)
  • FindingsBug, NoiseSignature (errors known to be harmless), Requirement
  • HistoryCommit, HumanDecision (approve / reject / annotate)

The edges are what make it useful:

  • Flow —visits→ Page —calls→ ApiEndpoint
  • Page —renders→ Component —contains→ Element
  • TestCase —covers→ Flow · TestCase —justified_by→ Requirement
  • TestCase —touches→ SourceFile (from coverage data)
  • Bug —found_in→ Run · Bug —affects→ Component · Bug —likely_caused_by→ Commit
  • Evidence —matches→ NoiseSignature
  • HumanDecision —confirmed | rejected→ Bug / TestCase
// how it plugs into the pipeline

Memory doesn't add a step — it wraps every existing one in the same five-part loop:

a

Look up

Before acting, the agent queries the graph. Is this error a known noise signature? Is there a working locator for this element? Has this flow been planned, and has nothing it touches changed since?

b

Try deterministic tools

If memory doesn't answer it, rules, parsers, crawlers and diffing get the next shot (§06).

c

Escalate to the LLM

Only what's still unanswered reaches a model — with the relevant neighbourhood of the graph as context, rather than the whole app.

d

Write back

The answer becomes a node or edge, stamped with provenance (rules / LLM / human), a confidence level, and the Langfuse trace ID. Next time, step (a) answers it for free.

e

Invalidate on change

When a commit lands, changed files are followed through touches and renders edges, and every dependent node is marked stale until re-verified.

// what each agent reads and writes
AgentReads before actingWrites after
PlannerExisting flows, pages with no covering test, bug-prone componentsNew Page, Flow, ApiEndpoint nodes from crawls
Test genLocators that worked, similar tests to template from, test data that passed a form's validationTestCase nodes linked to flows and requirements
ExecutorStored auth sessions, slow endpoints to mockRun, Evidence pointers, touches edges
AnalyzerNoise signatures, past bugs on the same component, recent commits touching itBug, NoiseSignature, dedup links
ReporterLinked tickets, affected requirements, owning moduleTicket IDs back onto Bug nodes
OrchestratorDiff → touches → affected tests—
Review queueLow-confidence facts awaiting a humanHumanDecision nodes (also sent to Langfuse as scores)
// features that become graph queries

Several items in the feature catalog stop being separate subsystems:

  • Coverage gap analysis — pages with no incoming covers path.
  • Test impact analysis — changed files → touches → tests to rerun.
  • Traceability — test → justified_by → requirement.
  • Dedup & regression clustering — failures sharing a component and an error signature.
  • Root-cause suggestion — bug → component → recent commits touching it.
  • Per-module health — bug and coverage counts rolled up per component.
// trust rules
  • Provenance on everything — created by rules, LLM or human, plus the trace ID that produced it.
  • Human beats model — human-confirmed facts outrank LLM-inferred ones when they conflict.
  • No silent suppression — an LLM-inferred NoiseSignature never auto-hides a failure until a human confirms it.
  • Stale until proven — invalidated nodes can inform an agent but can't short-circuit a decision.
// storage

Start in the Postgres that's already in the stack — two tables, typed JSONB properties, and pgvector for fuzzy matching ("is this error similar to a known one?"). The traversals Testomation needs are mostly one to three hops, which recursive CTEs handle fine. Move to a dedicated graph database only if traversals get deep or slow.

-- nodes: anything the system knows about
CREATE TABLE mem_node (
  id          uuid PRIMARY KEY,
  kind        text NOT NULL,        -- 'Page', 'Bug', 'NoiseSignature', ...
  key         text NOT NULL,        -- natural key, e.g. route or error hash
  props       jsonb NOT NULL DEFAULT '{}',
  embedding   vector(1024),         -- optional, for fuzzy matching
  source      text NOT NULL,        -- 'rules' | 'llm' | 'human'
  confidence  real NOT NULL,
  trace_id    text,                 -- Langfuse trace that created it
  stale       boolean NOT NULL DEFAULT false,
  updated_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (kind, key)
);

-- edges: how those things relate
CREATE TABLE mem_edge (
  src     uuid REFERENCES mem_node(id),
  rel     text NOT NULL,            -- 'covers', 'touches', 'affects', ...
  dst     uuid REFERENCES mem_node(id),
  props   jsonb NOT NULL DEFAULT '{}',
  source  text NOT NULL,
  PRIMARY KEY (src, rel, dst)
);
06

Cost strategy

The rule: the LLM writes and interprets tests; it never runs them. A test generated once and run a thousand times by Playwright costs one generation. LLM spend then scales with how much the app changes, not with how often it's tested.

// deterministic first, LLM for the residue
StageDeterministic firstLLM only for
PlanRouter / sitemap / OpenAPI parsing; state-graph crawlerNaming and ranking flows; inferring business rules
GenerateTemplates for common patterns; boundary values from HTML attributes; schema-driven API tests; Faker for dataNovel multi-step flows
ExecutePlain Playwright with role-based / test-id locatorsNothing
AnalyzeAssertions, status codes, console allowlist, axe-core, perceptual diff, flake historyFailures matching no known signature
DedupeHash of normalised error signatureBorderline matches (embeddings first)
ReportTemplated tickets and messagesOptional summary on filed bugs
ImpactCoverage mapping via the memory graphNothing
// making the remaining calls cheap
  • Memory before model — the graph is the cache; a question answered once isn't paid for again.
  • Change-triggered — re-plan and regenerate only what a diff touched.
  • Model tiers — a small, fast model for classification and dedup; a larger one for planning and generation.
  • Text over pixels — send the accessibility tree or a trimmed DOM; screenshots only for suspected visual bugs.
  • Prompt caching & batch — app context repeats across calls; nightly planning doesn't need to be real-time.
  • Hard per-run budget — once a PR's budget is spent, remaining items go to the review queue instead.
// exploratory testing without a vision loop

Before reaching for the vision agent, run monkey/fuzz interaction and coverage-guided crawling, checking invariants on every state reached: no console errors, no 5xx responses, no axe violations, nothing overflowing the viewport. The vision agent becomes an occasional, budgeted deep pass on high-value flows.

07

Observability with Langfuse

Langfuse is the record of what each agent did, what it cost, and whether it was right. Its trace model maps cleanly onto Testomation:

LangfuseTestomation
SessionOne PR or test run — run-<pr>-<sha>
TraceOne agent job — "plan checkout flows", "triage failure #182"
SpanA non-LLM step — memory lookup, crawl, rules-engine triage
GenerationAn actual model call, with tokens, cost and prompt version
Tagsagent:analyzer, trigger:pr, repo:web-app, model-tier:small
ScoresHuman verdicts from the review queue
// instrumentation sketch
from anthropic import Anthropic
from opentelemetry.instrumentation.anthropic import AnthropicInstrumentor
from langfuse import observe, get_client, propagate_attributes

AnthropicInstrumentor().instrument()   # every Claude call → a generation
langfuse = get_client()                # reads LANGFUSE_* env vars

@observe(name="analyzer.triage", capture_input=False)  # no raw DOM / screenshots
def triage_failure(failure, run_id):
    with propagate_attributes(session_id=run_id, tags=["agent:analyzer"]):
        hit = memory.lookup_noise(failure.signature)       # (a) memory
        langfuse.update_current_span(metadata={"memory_hit": hit is not None})
        if hit and hit.source == "human":
            return hit.verdict

        verdict = rules_engine.classify(failure)           # (b) deterministic
        if verdict.confident:
            memory.write(verdict, source="rules")
            return verdict

        verdict = llm_classify(failure)                    # (c) model
        memory.write(verdict, source="llm",               # (d) write back
                     trace_id=langfuse.get_current_trace_id())
        return verdict

In Temporal activities or other short-lived workers, call langfuse.flush() before the process exits.

// how it ties to memory and cost
  • Graph ↔ trace links — every LLM-created node stores its trace ID, so any bug or test can be traced back to the exact reasoning and prompt version that produced it.
  • Cache rate — a memory_hit flag on every span shows the share of decisions memory answered, which should climb as the graph matures.
  • Budget enforcement — the orchestrator queries spend-so-far per session and stops escalating once a run's budget is used.
  • Analyzer accuracy — review-queue decisions are written back as scores, giving real precision numbers and telling you when a confidence threshold is safe to raise.
  • LangGraph tracing — Langfuse's LangChain callback handler traces LangGraph runs, so each graph node appears as its own span without extra instrumentation.
  • Prompt management & datasets — prompts are versioned in Langfuse; hard triage cases become a regression dataset to rerun on every prompt change or model downgrade.
Self-host it. Traces touch customer app content. Run Langfuse inside your own infrastructure, keep capture_input=False on anything that sees page content, and log evidence IDs rather than raw payloads.
08

Agent runtime: LangGraph

Testomation has two different orchestration problems, and they want different tools. Running hundreds of tests across a browser pool, retrying failed jobs and scheduling a run per PR is distributed job work. Deciding, inside one agent, whether memory answered a question, whether the rules engine is sure, and whether to ask a human is reasoning control flow. The split: Temporal on the outside, LangGraph on the inside.

ConcernTemporal / Redis workersLangGraph
Unit of workA whole run: impact analysis, test fan-out, reportingOne agent's decision on one item
ParallelismHundreds of tests across a browser poolWithin a single graph, if at all
DurabilityWorkflow survives worker crashes and redeploysGraph state checkpointed per step to Postgres
BranchingFixed pipeline of activitiesConditional edges: memory hit, confidence, budget
Humans—interrupt() pauses a graph until the review queue answers
// how a run nests
Temporal workflow: "PR #412"
 ├─ activity: impact analysis         plain code · memory-graph query
 ├─ activity: run affected tests      plain Playwright · fanned out across the pool
 ├─ activity: triage failures      →  Analyzer graph, one thread per failure
 ├─ activity: generate missing tests → Test-gen graph (generate → run → repair, capped)
 └─ activity: report                 plain code · templates

Each activity that needs reasoning invokes a small, focused graph. Everything else stays plain code.

// where LangGraph is used — and where it isn't
  • Analyzer — first, and the best fitMemory → rules → LLM → confidence gate → file or pause for review. The graph drawn below.
  • Test genGenerate → run → read the error → repair, with a hard retry cap so a stubborn flow can't burn tokens.
  • PlannerCrawl → parse → rank → go back for more detail on high-value areas.
  • Exploratory agentA natural loop that stops on budget exhausted or no new states found.
  • Not: scripted executionPlaywright running a generated test has no decisions to make; a graph adds only overhead.
  • Not: reporterTemplated output — a plain function is enough.
  • Not: outer orchestrationFan-out, retries and scheduling across workers stay in Temporal.
  • Not: the memory graphLangGraph's own long-term store is key-value, not a linked graph. Agents reach the Postgres memory graph through lookup and write-back nodes.

// sketch
from typing import TypedDict, Optional
from langgraph.graph import StateGraph, START, END
from langgraph.types import interrupt, Command
from langgraph.checkpoint.postgres import PostgresSaver
from langfuse.langchain import CallbackHandler

class Triage(TypedDict):
    failure: dict
    verdict: Optional[dict]
    confidence: float
    source: str                     # 'memory' | 'rules' | 'llm' | 'human'

def memory_lookup(s): ...           # plain Python, no model
def rules_engine(s):  ...           # plain Python, no model
def llm_classify(s):  ...           # the ONLY node that calls Claude;
                                    # sets confidence=0 if the run's budget is spent
def review(s):
    decision = interrupt({"failure_id": s["failure"]["id"]})   # graph pauses here
    return {"verdict": decision, "source": "human", "confidence": 1.0}
def write_back(s):    ...           # memory.write(verdict, source=s["source"], ...)

g = StateGraph(Triage)
for name, fn in [("memory", memory_lookup), ("rules", rules_engine),
                 ("llm", llm_classify), ("review", review), ("write", write_back)]:
    g.add_node(name, fn)

g.add_edge(START, "memory")
g.add_conditional_edges("memory", lambda s: "write" if s["source"] == "human" else "rules")
g.add_conditional_edges("rules",  lambda s: "write" if s["confidence"] >= 0.9 else "llm")
g.add_conditional_edges("llm",    lambda s: "write" if s["confidence"] >= 0.8 else "review")
g.add_edge("review", "write")
g.add_edge("write", END)

analyzer = g.compile(checkpointer=PostgresSaver(conn))   # same Postgres as memory

# inside a Temporal activity
cfg = {"configurable": {"thread_id": f"triage-{failure['id']}"},
       "callbacks": [CallbackHandler()]}                  # every node -> Langfuse span
analyzer.invoke({"failure": failure}, config=cfg)

# later, when a reviewer decides in the review queue
analyzer.invoke(Command(resume=reviewer_decision), config=cfg)
// what this buys
  • Cost rules enforced in code — the order memory → rules → model is the graph's shape, not a convention each agent has to remember.
  • Review queue for free — an interrupted graph is a review-queue item. The reviewer's decision resumes it, the result is written to memory as human-sourced, and it's sent to Langfuse as a score.
  • Crash-safe exploration — checkpoints in the same Postgres as the memory graph mean a long exploratory session resumes where it stopped.
  • Visible paths — with the Langfuse handler attached, every node is a span, so you can see how many failures took the free path versus the model path.
Adopt it incrementally. Build the analyzer as a graph first, where branching and review pauses matter most. Move other agents over only when their logic actually branches or loops — a straight-line agent doesn't need a framework.

Design risks worth building around

Self-healing can hide real bugs

A tool that quietly swaps in a new selector when one breaks and re-runs isn't the same as understanding why it broke. If a button moved because a layout regressed, silently "healing" the locator buries the exact bug the test existed to catch. The Analyzer should treat selector drift as a signal to flag, not a problem to auto-resolve.

Vision-agent runs are slow and non-deterministic

Great for exploratory bug-hunting, bad for a CI gate that needs to be fast and repeatable. Keep scripted regression and agentic exploration as two distinct modes rather than asking one agent to do both jobs well.

Memory can learn the wrong lesson

If the Analyzer once wrongly decides a 500 error is noise and saves that as a signature, it will ignore that bug on every future run. It's the same failure mode as self-healing, made permanent. LLM-inferred suppressions must stay in the review queue until a human confirms them.

Stale memory looks like fresh knowledge

A locator or flow that was correct last month may not be today. Invalidation on every commit, plus treating stale nodes as hints rather than answers, keeps old facts from short-circuiting new decisions.

Cost optimisation can quietly cost coverage

A tight budget that routes everything to the review queue just moves the work to humans. Watch the review-queue size in Langfuse next to spend; if one drops while the other climbs, the budget is set wrong.

Two orchestrators can blur into one

If LangGraph starts handling fan-out and retries, or Temporal starts encoding agent decisions, you get two half-overlapping systems and state that lives in both. Keep the line sharp: Temporal owns jobs and workers; LangGraph owns decisions within one item.

Build order

PHASE 1

Prove the plumbing

A Playwright executor that runs a hand-written test and captures the full evidence bundle. No AI yet — get ingestion, execution, and evidence storage solid first. Create the memory graph schema now: tests, runs and evidence pointers are its first nodes, and coverage data gives the first touches edges.

PHASE 2

Generate from plain English

A test-gen agent that turns a described flow into working Playwright code. Wire up Langfuse and the per-run budget before this first model call, so cost is visible from day one. Generated tests land in memory linked to the flow they cover. Keep the repair loop as plain code for now — no framework yet.

PHASE 3

Plan the coverage

A planner built as crawler + parser first, with the LLM ranking and naming flows. It populates Page, Flow and ApiEndpoint nodes, and re-plans only what a diff touches.

PHASE 4

Tell bugs from noise

An analyzer that runs as a rules engine with an LLM fallback, classifies pass/fail from evidence and writes a human-readable bug report, plus a review queue for anything it isn't confident about. This is where memory starts paying off: noise signatures and human decisions accumulate, and review verdicts flow into Langfuse as scores. Build it as the first LangGraph graph: interrupt() powers the review queue and checkpoints live in Postgres. Move the test-gen repair loop onto LangGraph here too once the pattern is proven.

PHASE 5

Go exploratory

Fuzzing and coverage-guided crawling with invariant checks first, then the vision-based agent as a budgeted deep pass (a LangGraph loop that stops when budget or new states run out), plus flaky-test quarantine and visual regression diffing — the trio that turns a test runner into something that finds bugs on its own.

PHASE 6

Platformize

CI/CD plugins, dashboard and trend analytics (read straight from the memory graph and Langfuse metrics), production synthetic monitoring, RBAC, and the plugin architecture — the features that let other teams adopt it without your help.
