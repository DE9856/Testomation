v0.6 — project brief
// project brief

Testomation

An autonomous software testing platform. It reads a codebase or app, decides what needs testing, writes the test cases itself, drives a real browser to run them, tells bugs apart from noise, and reports back — with minimal humans in the loop. It runs entirely on one laptop, on free and local tools.

00

Overview

Traditional test automation still needs a human to decide what to test and to write the script. Testomation moves both of those jobs to an AI agent: one that reasons about the application the way a QA engineer would, generates its own coverage, and only asks for a human when it isn't sure whether something is actually broken.

The goal isn't to replace scripted regression testing — it's to sit alongside it, filling the gap between "what we remembered to test" and "what the app can actually do."

Ground rules for v0.6

  • Free and local — everything runs on one laptop. No paid APIs or hosted services in the product.
  • Ollama at runtime — every model call the product makes goes to local models served by Ollama.
  • Claude for building — Claude (Claude Code) is the assistant used to build Testomation. It is not part of the product's runtime.
  • Playwright does the running — Playwright Test handles execution, parallel workers, retries, traces and screenshots. Testomation doesn't rebuild any of that.

What changed since v0.5

  • Spike before infrastructure — a throwaway feasibility spike tests whether local models are good enough before any plumbing is built. §15
  • Triage for any Playwright suite — testomation import points the analyzer at an existing Playwright report, so it's useful from phase 2. §04
  • All approved specs run every run — a wrong impact map can't hide a regression; impact analysis now only scopes model work. §03
  • Freshness from basis hashes — memory records the file and page-structure hashes it was based on, so invalidation is precise and a revert makes memory fresh again. §06
  • Confidence from logprobs and labelled neighbours — one model call instead of three samples, and a score that can be calibrated. §09
  • Batched repair rounds and one model by default — the model and the browsers never compete for RAM, and the large tier must earn its place. §05 §10
  • LangGraph only for exploration — the analyzer is a plain-Python cascade; review is asynchronous, so nothing pauses or resumes. §09
  • Typed tables and claims on edges — constraints where the volume is, and humans can overrule inferred links. §06
  • Langfuse from phase 3 — OpenTelemetry spans go to a local file until the first model call, saving 2–3 GB of RAM. §08
  • Replay benchmark tier — analyzer changes are gated in minutes on recorded evidence. §11
  • One schema source, origin guard, helper steps — no drift between Python and TypeScript, specs stay on the target, and the vocabulary can grow without becoming code. §05

How it differs from Playwright Test Agents

Playwright ships official Planner, Generator and Healer agents. They explore an app, write a Markdown test plan, generate tests and repair failing ones. They run inside a coding-agent tool, using that tool's model. That overlaps Testomation's planning and generation, so the differences are deliberate:

Playwright Test AgentsTestomation
Test output.spec.ts codeJSON specs; nothing a model writes is executed
Failing testsHealer repairs themApproved specs never self-heal; drift is a review item
ModelsWhatever the coding tool usesLocal Ollama models only
Memory—Memory graph with claims, provenance and freshness
Bug vs noise—Analyzer cascade with a review queue
Measuring itself—Seeded-bug benchmark gates every change

Their Generator and Healer aren't reused, because they'd break the "no model-written code" and "no self-healing" principles. Whether the planner should emit a human-editable Markdown plan the way theirs does is an open question.

Cross-cutting layers

None of them adds a new pipeline step; they change how every existing step behaves.

  • Memory graph — a shared, persistent map of the app under test and everything Testomation has learned about it. Every agent reads it before acting and writes back after. §06
  • Cost & compute strategy — the LLM authors and interprets tests but never runs them. Deterministic tools go first; the model only sees what they couldn't settle. §07
  • Observability — every agent job is traced, including the ones that never called a model: an OpenTelemetry file first, self-hosted Langfuse from phase 3. §08
  • Agent runtime — the pipeline runner and Playwright Test run the jobs; plain-Python agents make the decisions (memory → rules → neighbours → model → human review); LangGraph runs only the exploration loop. §09

They reinforce each other: memory is what makes most LLM calls unnecessary, the analyzer's cascade enforces "memory and rules before the model" in code, traces prove it's working, and the benchmark is how you know it's right.

01

The pipeline

01

Ingest

Pull in the target. For the MVP: a locally running web app (URL) and its repository. For triage alone, an existing Playwright project's report is enough. OpenAPI specs, design files and user stories come later.

02

Plan

An agent reasons about what should be tested — user flows, edge cases, boundary conditions, negative paths — and produces a structured coverage plan.

03

Generate

Each planned flow becomes a JSON test spec: a list of steps with role- or label-based targets and assertions, validated against a schema.

04

Execute

Playwright Test runs every approved spec through one generic spec runner, with no model loaded. Traces, screenshots, DOM snapshots, console output and network traffic are captured.

05

Analyze & report

Evidence is compared against expected behaviour, classified and deduped, then written to a local report with repro steps and links to the evidence.

Every step, same loop: check the memory graph → try deterministic tools → call a local model only for what's still unanswered → write the result back to memory as a claim with provenance → trace the whole job. In code, that loop is a plain-Python cascade in each agent; LangGraph runs only the exploration loop. Details in §06 and §09.
02

Feature catalog

Everything below is a candidate feature, grouped by where it sits in the system. core marks what an MVP needs to be useful at all; later marks what turns it from a working tool into a platform. Amber cards inside a core group are individually later.

Planning & test generation

core
  • Autonomous flow discoveryCrawls or reads the app and proposes the user flows worth testing, without being told what they are.
  • Natural-language test authoringA human types "test that guest checkout fails without an email" and gets a runnable spec.
  • Structured test specsTests are JSON specs run by one Playwright runner. The model fills a schema; it never writes executable code. Named helper steps cover what the vocabulary can't.
  • Edge-case & negative-path enumerationGenerates boundary values, invalid inputs, and error states alongside the happy path.
  • Coverage gap analysisFlags flows and routes that exist in the app but have no test touching them.
  • Requirement-to-test traceabilityLinks each generated test to the business rule that justified it — inferred by the planner and confirmed at approval in the MVP; user stories later.
  • Synthetic test data generationFaker references in specs produce realistic names, emails and files at run time, without real PII.
  • Change-scoped model workGiven a code diff, works out which flows to re-plan and which specs to regenerate. Every approved spec still runs. Starts from a static route → file map; runtime coverage refines it.

Memory & knowledge

core
  • Persistent app knowledge graphPages, flows, tests, bugs, commits and human decisions stored as linked nodes, so related things stay together across runs.
  • Memory-first lookupsAgents check what's already known before reasoning from scratch; answers get cached as graph facts.
  • Claims with provenanceEvery verdict — and every disputed link — records who asserted it (rules, neighbour vote, LLM, human), how sure it is, and the trace behind it. Conflicting claims coexist.
  • Change-aware freshnessEach claim records the file and page-structure hashes it was based on. It's stale once they change, and fresh again after a revert.

Execution

core
  • Parallel runsPlaywright Test workers fan specs out on the laptop. The model is unloaded while specs run, so more workers fit; two while one is loaded (exploration).
  • App state resetThe target app's seeded database is restored before each run, and each test gets its own synthetic user so parallel workers don't collide.
  • Browser matrixChromium and Firefox on the laptop. WebKit through the official Playwright container, since Playwright doesn't officially support Fedora.
  • Responsive viewport testingReruns flows at phone, tablet, and desktop breakpoints.
  • Visual regression diffingPlaywright's built-in screenshot comparison against a baseline, with a highlighted diff.
  • Combined API + UI verificationCalls the backend directly to set up state, then verifies the frontend reflects it correctly.
  • Accessibility auditingRuns axe-core on every page visited and reports WCAG violations.
  • Auth & session handlingSaved Playwright storage state, so every test doesn't have to log in from scratch.
  • Third-party mockingRoute interception and HAR replay stub flaky or rate-limited services, so failures are the app's fault, not a dependency's.
  • Per-branch environmentsA throwaway local compose environment per branch, so tests run against that exact change.
  • Exploratory session recordingThe agent free-roams the app like a curious user, never leaving its origin, and every click, scroll, and state change is logged — findings replay as draft specs. This is how it finds the bugs no one thought to write a test for.

Bug detection & analysis

core
  • Triage for existing Playwright suites newtestomation import points the analyzer at any Playwright project's report and traces — no Testomation specs needed.
  • Console & network error classificationSeparates real application errors from expected noise (ad blockers, analytics failures).
  • Severity & priority scoringRanks findings so a blocked checkout outranks a misaligned footer.
  • DeduplicationMatches a new failure against known bugs by error-signature hash first, local embeddings for borderline cases — as duplicate links a human can reject.
  • Confidence scoringThe label probability from one model call (logprobs), a vote of similar failures humans already labelled, and the rules signal — calibrated on the benchmark, not the model's self-report.
  • Flaky test detection & quarantineTracks pass/fail history per test and isolates ones that fail inconsistently. Runs under heavy machine load are excluded from the flake signal.
  • Multimodal visual bug detectionA small local vision model looks at suspected layout bugs that a pixel diff flagged but can't explain.
  • Root-cause suggestionCorrelates a failure's timing against recent commits and proposes which change likely caused it.
  • Regression clusteringGroups multiple failures that stem from the same underlying bug into one report instead of ten.

Human-in-the-loop & collaboration

core
  • Review queueA testomation review command to approve, reject, or edit anything the agent wasn't confident about. A local web UI comes later.
  • One-click test approvalGenerated specs start as drafts; a human promotes them into the regression suite.
  • Local run reportAn HTML/Markdown summary per run with repro steps and links to traces, next to Playwright's own HTML report.
  • Desktop notificationsA notification when a run finishes or a confirmed bug is found.
  • Inline annotationComment directly on a screenshot or trace step to explain context the agent missed.
  • GitHub Issues / Jira / SlackBugs become tickets and channel posts once the tool leaves the laptop.
  • Audit trailEvery decision the agent made — why it generated a test, why it flagged something — is logged and reviewable through claims and Langfuse traces.

Evaluating Testomation itself

core
  • Seeded-bug benchmarkA local target app with a catalogue of known bugs, each switchable on or off, gives ground truth. Only mutants a user could notice count.
  • Regression runs on every changeAnalyzer changes rerun the replay tier (minutes); generation and model changes rerun the full benchmark, which also runs nightly.
  • Threshold calibrationConfidence gates are set from benchmark precision and recall — reported as ranges over three runs — instead of guessed, then refined with review-queue scores.

Reporting & analytics

later
  • Live dashboardCoverage, pass rate, flake rate, and open-bug count at a glance.
  • Trend graphs per releaseShows whether quality is improving or degrading release over release.
  • Per-module health scoringSurfaces which parts of the app are the most bug-prone or worst-covered.
  • Exportable reportsPDF or CSV summaries for stakeholders who don't live in the dashboard.
  • LLM usage trackingTokens, latency and calls per run and per agent via Langfuse. Local models cost no money, but they cost time.
  • Custom alerting rules"Notify me only if a payment flow breaks" instead of every flaky assertion.

Platform & integration

later
  • CI/CD pluginsNative steps for GitHub Actions, GitLab CI, and CircleCI so runs trigger on every PR.
  • Event-driven triggersRun on push, on deploy, nightly, or on demand — not just on a fixed schedule.
  • Public API / SDKProgrammatic control for teams who want to script Testomation into their own tooling.
  • Multi-project supportSeveral apps under test with isolated memory. The schema carries a project column from day one.
  • Production synthetic monitoringRuns a light version of the suite continuously against production to catch live incidents, not just pre-release bugs.
  • Plugin architectureLets teams add custom checks (brand guidelines, internal compliance rules) without forking the core.
  • Test selectionRun only the specs a diff affects, once running every approved spec gets too slow.

Security & governance

later
  • Secrets managementSpecs reference credentials as $secret names; values are injected from the environment at run time and never stored.
  • PII redactionMasks sensitive data in screenshots and logs before they're stored or shared.
  • Role-based access controlControls who can approve tests, view evidence, or change production-monitoring schedules.
  • Sandboxed executionEvery browser session runs isolated, and because tests are specs rather than code, nothing a model writes is executed on the host. Specs and exploration never leave the target origin.

Everything runs on one laptop. Test specs live in the graph as TestCase nodes; the executor runs every approved one with Playwright Test. The pipeline runner and the agents are plain Python; the exploration loop is the only LangGraph graph. The review queue lists open review_item rows. Langfuse starts in phase 3 — until then, stage spans go to a local OpenTelemetry file.

// the model path

One small client wraps every model call. It returns the parsed value plus the label probability (from logprobs) when the schema has a label. Swapping Ollama for any other OpenAI-compatible server later is a config change.

// how a run flows
testomation run --pr 412              pipeline runner · stage state in Postgres
 ├─ stage: refresh basis + scope       plain code · git blob SHAs · memory-graph query
 ├─ stage: run approved specs          model unloaded · npx playwright test · retries=1
 ├─ stage: triage failures             plain code · memory → rules → neighbours → model
 ├─ stage: generate missing tests      plain code · ≤3 rounds: generate → unload → run → repair
 └─ stage: report                      plain code · local HTML / Markdown

Every approved spec runs every run — execution is cheap and a wrong impact map must never hide a regression. Impact analysis (a static route → file map, refined by coverage) only decides which flows to re-plan and which specs to regenerate. The model is unloaded whenever browsers run, except during exploration.

// two languages, one boundary

Agents, memory, the pipeline and the exploration graph are Python. The spec runner is TypeScript, because Playwright Test's TypeScript runner has the most features. They meet only through files: Python writes the run's specs as JSON, Playwright writes a JSON results file plus traces, and Python ingests both — or ingests any other Playwright project's report through testomation import.

The spec schema has one source, schemas/test-spec.schema.json. Pydantic models and TypeScript types are generated from it, and shared example specs are validated by both sides, so the brain and the hands can't drift.

04

Components

Planner agent

Turns the app into a flow graph

Reads routes, components, API schema, or a live crawl of the app to build a map of user flows — "signup → verify email → onboarding," "add to cart → checkout → payment failure." The structural map comes from deterministic parsing, a state-graph crawler and Playwright aria snapshots; the small local model's job is narrower — naming flows, ranking what matters, and inferring business rules a crawler can't see ("checkout should fail without an email"). Inferred rules become Requirement nodes that a human confirms at approval.

Plain code. Writes Page, Component, Element, Flow and ApiEndpoint nodes with an aria basis, and only re-plans pages whose basis changed.

Test generation agentchanged

Converts a flow into a JSON test spec

  • Spec, not code — the model fills a JSON schema (steps, role/label targets, assertions). Ollama's structured output constrains decoding to that schema, so small models can't produce invalid tests.
  • Deterministic execution — one generic Playwright runner executes every spec. Same determinism and speed as scripted tests, no generated code on the host.
  • Agents for exploration only — live, unscripted bug-hunting stays a separate executor mode.

Before generating, it pulls targets that worked before and similar specs from memory to use as templates. Common patterns (login, form submit, CRUD) come from templates with no model call at all. Novel flows use the small model (the large tier only if the benchmark earns it) and go through up to three batched repair rounds: generate or repair every pending draft, unload the model, run every draft, repeat. Repairs may change targets and add waits; changing or removing an assertion goes to review. See §05.

Executorchanged

Actually drives the browser

Two modes, kept separate rather than merged into one agent:

  • Playwright Test + spec runner — runs every approved spec with workers and retries, with no model loaded. Fast and repeatable; the right choice for regression gates.
  • Exploratory agent loop — aria snapshot → local model picks the next spec step → execute → repeat, with invariant checks on every state. The one LangGraph loop; a small vision model is optional. Slower, but it finds the bugs a spec wasn't written to look for.

Evidence comes from Playwright itself: the trace file (screenshots, DOM snapshots, console, network), failure screenshots and video, axe results, and Chromium JS coverage per test. Evidence is written to data/evidence/<run>/ and recorded on result rows; coverage becomes the touches edges that scope model work. In both modes, navigation off the target origin is aborted.

Importernew

Lets the analyzer work on suites Testomation didn't write

testomation import reads any Playwright project's JSON report with its traces and attachments, writes a Run and result rows, and hands them to the normal triage and report stages. Failures map to steps through test.step titles when present, otherwise through the failing locator and the trace's last action.

Analyzer agentchanged

Decides what's actually a bug

Reasons over the evidence bundle rather than a single assertion. Signal sources include failed assertions, console exceptions, 4xx/5xx network responses, visual regressions, dead-end navigation states, and accessibility violations. Input is a result from the spec runner or from an imported Playwright suite.

A plain-Python cascade: memory, then a rules engine (known noise signatures, status codes, axe-core, screenshot diffs, flake history), then a vote of labelled neighbours — similar failures humans already decided. Only what's still unsettled reaches the small local model, in one call whose label probability comes from logprobs. Confidence is a calibrated mix of that probability, the neighbour vote and the rules signal — never the model's self-report (§09).

Reporter

Closes the loop with humans

Writes a local HTML/Markdown report per run — confirmed bugs, repro steps, links to traces and screenshots — next to Playwright's HTML report, and sends a desktop notification. GitHub Issues, Jira and Slack come once the tool leaves the laptop.

Review queuechanged

Where uncertain decisions wait for a human

A review item is a row in a review_item table: what the agent would have decided, its score, the evidence and the trace. testomation review shows each item, opens the trace with npx playwright show-trace, and records the decision. The decision becomes a human claim and a HumanDecision node, goes to traces as a score, and is applied with the same function the analyzer uses. No graph is paused or resumed. testomation approve promotes draft specs and confirms their requirement.

Pipeline runnerchanged

Keeps everything coordinated

testomation run executes a fixed sequence of stages and records each stage's state in Postgres, so a crashed run resumes from the last completed stage. It refreshes file hashes, runs every approved spec, enforces the per-run compute budget, uses the memory graph to decide which flows to re-plan and which specs to regenerate, unloads the model before any stage that runs browsers, and drives the repair rounds. Fan-out and retries are Playwright Test's job. Temporal returns only if Testomation spreads across machines.

Exploration runtime (LangGraph)

Runs the one long loop

Snapshot → check invariants → choose an action → act, checkpointed to Postgres so a long session resumes where it stopped. This is the only place LangGraph is used. See §09.

Memory graph

Shared knowledge every agent reads and writes

Not an agent — a store. It holds the relationships between pages, flows, specs, bugs, commits and human decisions, typed tables for the core records, result rows, and the claims each source made about them. See §06.

Observability

Records what every agent did and how long it took

OpenTelemetry spans to a local file in phases 0–2; self-hosted Langfuse from phase 3. Each agent job is a trace. Model calls appear as generations with tokens and latency; deterministic steps appear as spans, so skipped model calls are visible too. See §08.

05

Test spec

A test is data, not code. The model fills a JSON schema; one Playwright runner interprets it. This suits small local models, which fill a fixed schema far more reliably than they write free-form code. It also means generated tests are easy to diff, dedupe, store in the graph and repair — and nothing a model writes is executed on the laptop.

{
  "spec_version": 1,
  "id": "checkout.guest.no-email",
  "flow": "guest-checkout",
  "requirement": "checkout.email-required",
  "steps": [
    { "action": "goto",   "url": "/cart" },
    { "action": "click",  "target": { "role": "button", "name": "Checkout" } },
    { "action": "fill",   "target": { "label": "Name" },  "value": { "$faker": "person.fullName" } },
    { "action": "fill",   "target": { "label": "Email" }, "value": "" },
    { "action": "click",  "target": { "role": "button", "name": "Place order" } },
    { "action": "expect", "target": { "role": "alert" },  "assert": "hasText", "value": "Email is required" }
  ]
}

requirement is optional. In the MVP it names a business rule the planner inferred or a human added at approval.

// step vocabulary
ActionFieldsNotes
gotourlA path relative to the target's base URL — must start with /
click · hovertarget
fill · selecttarget, valueValue may be a literal or a reference
check · unchecktarget
presskey, optional target
uploadtarget, fileFile is a $fixture reference
wait_fortarget, statevisible · hidden
expecttarget or page, assert, valuevisible · hidden · hasText · hasValue · count · url · ariaSnapshot

// targets and values
  • Targets — one of testid, role + name, label, placeholder, text, in that order of preference. CSS and XPath aren't in the schema.
  • $faker — synthetic data generated at run time ({"$faker": "internet.email", "as": "email"}); {"$var": "email"} reuses it later in the spec.
  • $secret — a credential name, resolved from the environment at run time and never stored.
  • $fixture — a file from the project's fixtures folder.
// one schema, helpers, origin guard
  • One schema source — schemas/test-spec.schema.json is the only definition of a spec. Pydantic models and TypeScript types are generated from it; example specs in schemas/examples/ are validated by both sides.
  • Decoder-friendly — the spike showed Ollama silently drops schema parts it can't convert, so every union branch is a complete object, every pattern is anchored, the step list is capped, and name is only allowed on roles that can have one. The llm client rewrites patterns into the form Ollama's grammar accepts.
  • Helper steps — when specs need something the vocabulary can't express (dialogs, downloads, iframes, network assertions), a human writes a helper in runner/helpers/. Registered helper names are injected into the schema as an enum, so models can only name helpers that exist — they never write one. A widely used helper can be promoted into the core vocabulary with a spec_version bump.
  • Origin guard — goto and api paths must be relative, and the runner aborts top-level navigation to any origin other than the target app's. Exploration uses the same guard.
// runner, lifecycle, repair
  • Spec runner — one Playwright test file registers a test() per spec and wraps each step in test.step(), so steps show up by name in traces and reports. Fixtures add axe checks, coverage, an aria snapshot on failure, the origin guard and the helper registry.
  • Exporter (later) — turns a spec into a readable .spec.ts for anyone who wants to own a test outside Testomation.
  • Lifecycle — draft → approved → quarantined → retired, stored on the test_case row. Only approved specs run in regression — and all of them run, every run.
  • Batched repair rounds changed — up to three rounds: the model generates or repairs every pending draft, the model is unloaded, every draft runs, and failures go into the next round with the failing step, the error and the aria snapshot. Repairs may change targets or add waits. Changing or removing an expect needs review, because the failure might be a real bug. Still failing after round three → review queue.
  • Approved specs never self-heal — any change to an approved spec is a drift signal for the analyzer and a review item.
06

Memory graph

The memory graph is Testomation's long-term knowledge about the app under test: what exists, what's been tested, what broke, why, and what humans decided. It keeps useful things connected — a bug is linked to the component it affects, the commit that likely caused it, the run that found it and the result that proves it — so any agent can follow those links instead of re-deriving them.

// what it stores
  • App structurePage, Component, Element, ApiEndpoint, SourceFile
  • Test knowledgeFlow, TestCase (typed: spec and status), Run (typed)
  • FindingsBug (typed), NoiseSignature (typed; errors known to be harmless), Requirement
  • HistoryCommit (typed), HumanDecision (approve / reject / annotate)
  • Result rows, not nodes newOne row per test per run — outcome, failing step, error signature, evidence paths. They replace v0.5's Evidence nodes, because results are high-volume and nobody disputes them.

The edges are what make it useful:

  • Flow —visits→ Page —calls→ ApiEndpoint
  • Page —renders→ Component —contains→ Element
  • TestCase —covers→ Flow · TestCase —justified_by→ Requirement
  • TestCase —touches→ SourceFile (static map first, then coverage)
  • Commit —changes→ SourceFile
  • Bug —found_in→ Run · Bug —affects→ Component · Bug —likely_caused_by→ Commit
  • Bug —duplicate_of→ Bug new
  • HumanDecision —confirmed | rejected→ Bug / TestCase

A result row points at its Bug or NoiseSignature through its signature column, not through an edge.

// typed tables and claims
  • Typed tables — test_case, run, bug, noise_signature and git_commit sit 1:1 next to mem_node, with real constraints. They hold facts no source disputes: the spec, its status, timestamps, paths.
  • Claims — anything a source can get wrong (a verdict, a severity, whether a link holds) is a claim, stamped with its source (rules / knn / llm / human), confidence, trace ID and basis.
  • Claims on edges new — an edge row is the first claim about a link; later claims can dispute it, so a human can overrule an inferred likely_caused_by or duplicate_of.
// freshness from basis hashes

Every node, edge and claim records a basis: the hashes of what it was based on — file blob SHAs from git and normalised aria-snapshot hashes of the pages involved. A basis_state table holds the current hash of each key. A claim is fresh while its whole basis still matches, so nothing has to be rewritten when code changes:

  • Precise — a change to a shared file only affects claims based on it, instead of marking everything downstream stale.
  • Reversible — reverting a commit makes the old hashes match again, so the memory is fresh again.
  • Sees non-git changes — seed data or config changes still show up through aria hashes.

Aria snapshots are normalised before hashing (roles and accessible names kept; numbers, dates and generated values masked), or every run would produce a new hash. Commits and human decisions are immutable and have an empty basis.

// how it plugs into the pipeline

Memory doesn't add a step — it wraps every existing one in the same five-part loop:

a

Look up

Before acting, the agent queries the graph. Is this error a known noise signature? Is there a working target for this element? Has this flow been planned, and is that plan still fresh?

b

Try deterministic tools

If memory doesn't answer it, rules, parsers, crawlers, diffing and the labelled-neighbour vote get the next shot (§07).

c

Escalate to a local model

Only what's still unanswered reaches a model — with the relevant neighbourhood of the graph as context, rather than the whole app.

d

Write back

The answer becomes a claim, stamped with its source, a confidence level, the trace ID and its basis. Next time, step (a) answers it for free.

e

Check freshness

A claim counts only while its basis hashes match the current ones. Stale claims are shown as hints, never used as answers.

// trust rules
  • Provenance on everything — nodes, edges and claims all record their source, confidence, trace ID and basis.
  • Human beats model — for any node field or edge, the newest fresh human claim wins; otherwise the highest-confidence fresh claim. Losing claims are kept, not overwritten.
  • No silent suppression — a NoiseSignature inferred by a model (llm or knn) never auto-hides a failure until a human confirms it.
  • Stale until proven — stale nodes and claims can inform an agent but can't short-circuit a decision, even human ones.
// storage

Postgres with pgvector for fuzzy matching ("is this error similar to a known one?"). Traversals are mostly one to three hops, which recursive CTEs handle fine; a dedicated graph database is only worth it if they get deep or slow. Embedding size follows the local embedding model — 768 for the current candidate. The core tables (the full schema, with typed tables and review_item, is in docs/MEMORY_GRAPH.md):

A mem_fact view applies the "human beats model" rule to fresh claims, so agents read one resolved value per node and field; mem_edge_fact does the same for edges. In the MVP, Requirement nodes come from business rules the planner infers and from humans at spec approval.

Cost & compute strategy

The rule: the LLM writes and interprets tests; it never runs them. A spec generated once and run a thousand times by Playwright costs one generation. Model work then scales with how much the app changes, not with how often it's tested.

On a laptop with local models, the cost isn't money — it's VRAM, RAM and time. The rule protects those instead: every model call avoided is seconds saved and a browser worker that doesn't have to wait.

// deterministic first, LLM for the residue

PlanRouter / sitemap / OpenAPI parsing; state-graph crawler; aria snapshotsNaming and ranking flows; inferring business rules
GenerateSpec templates for common patterns; boundary values from HTML attributes; schema-driven API specs; Faker references; helper stepsNovel multi-step flows (as specs, never code)
ExecutePlaywright Test running every approved spec with role / test-id targetsNothing
AnalyzeAssertions, status codes, console allowlist, axe-core, screenshot diff, flake history, labelled-neighbour voteFailures nothing else settled — one call, label probability from logprobs
DedupeHash of normalised error signatureBorderline matches (local embeddings first)
ReportTemplated reports and notificationsOptional summary on filed bugs

// making the remaining calls cheap
  • Memory before model — the graph is the cache; a question answered once isn't asked again while its basis still matches.
  • Change-triggered — re-plan and regenerate only what a diff touched.
  • One model by default — a ~4B model that fits entirely on the GPU does all text work. A ~7–8B model with partial CPU offload is added only if the benchmark shows it's worth the swap.
  • One call, not three — the label probability comes from logprobs, so triage needs one call instead of three samples.
  • Structured output — JSON-schema-constrained decoding means no calls are wasted on output that can't be parsed.
  • Text over pixels — send the aria snapshot or a trimmed DOM; screenshots only for suspected visual bugs.
  • Group work by model — 4 GB of VRAM holds one model at a time. Batch embeddings, then small-model work, then any large-model work, and keep the model loaded for the whole batch.
  • Unload while browsers run — the runner unloads the model before spec runs and repair-round runs, so more workers fit and timeouts don't look like flakes.
  • Overnight batches — planning and generation for areas a PR didn't touch can run while the laptop is idle.
  • Hard per-run budget — a cap on model calls and model wall-clock time per run. Once it's spent, the analyzer skips the model step and remaining items usually go to the review queue.
// exploratory testing without a vision loop

Before reaching for any agent, run monkey/fuzz interaction and coverage-guided crawling, checking invariants on every state reached: no console errors, no 5xx responses, no axe violations, nothing overflowing the viewport. The exploratory agent then works on aria snapshots with a text model, choosing spec steps on the target origin only; a small vision model is an optional, budgeted deep pass on high-value flows.

Observability

Traces are the record of what each agent did, how long it took, and whether it was right. They come in two stages:

  • Phases 0–2: OpenTelemetry → a local file new — pipeline code uses the OpenTelemetry API with a file exporter (data/traces/<run>.jsonl). There are no model calls yet, so this saves the 2–3 GB of RAM the Langfuse stack needs.
  • Phase 3 on: Langfuse, self-hosted — brought up with its Docker Compose setup alongside the first model call. Its Python SDK is built on OpenTelemetry, so the same spans flow into it without changing pipeline code.

Langfuse's trace model maps cleanly onto Testomation:

from langfuse.openai import OpenAI     # drop-in client: every call → a generation

@observe(name="analyzer.triage", capture_input=False)  # no raw DOM / screenshots
def triage_failure(failure, run_id):
    with propagate_attributes(session_id=run_id, tags=["agent:analyzer"]):
        hit = memory.fresh_human_verdict(failure.signature)    # (a) memory
        langfuse.update_current_span(metadata={"memory_hit": hit is not None})
        if hit:
            return hit

        rule = rules_engine.classify(failure)                  # (b) deterministic
        if rule.confident:
            return memory.claim(failure, rule, source="rules")

        votes = memory.labelled_neighbours(failure)            # (b) embeddings, no generation
        if votes.decisive:
            return memory.claim(failure, votes.verdict, source="knn")

        p = llm_classify(llm, failure, tier="small")           # (c) one call, logprobs → p(label)
        verdict = calibrate(rule, votes, p)                    # gate + review_item: §09
        return memory.claim(failure, verdict, source="llm",    # (d) write back
                            trace_id=langfuse.get_current_trace_id())

Call langfuse.flush() before a short-lived worker or CLI command exits. The spike verifies that structured output with the spec schema and logprobs both work through the OpenAI-compatible endpoint and langfuse.openai; the fallback is Ollama's native client with a manual generation span.

// how it ties to memory and compute
  • Graph ↔ trace links — every model-created node and claim stores its trace ID, so any bug or spec can be traced back to the exact reasoning and prompt version that produced it.
  • Cache rate — a memory_hit flag on every span shows the share of decisions memory answered, which should climb as the graph matures.
  • Budget enforcement — the pipeline runner counts model calls and model time per session and stops escalating once a run's budget is used.
  • Analyzer accuracy — review-queue decisions are written back as scores, giving real precision numbers alongside the benchmark.
  • Exploration tracing — Langfuse's LangChain callback handler traces the exploration graph, so each of its nodes appears as its own span.
  • Prompt management & datasets — prompts are versioned in Langfuse; benchmark, replay and hard triage cases become datasets to rerun on every prompt change or model swap.
Local models have no price. Langfuse won't show a cost for them, so track tokens, latency and call counts instead — those are the numbers that matter on a laptop. Keep capture_input=False on anything that sees page content, and log evidence paths rather than raw payloads.

Agent runtime: pipeline for jobs, plain code for decisions

Testomation has three different control-flow problems. Running tests in parallel, retrying failures and moving a run through its stages is job work. Deciding, inside one agent, whether memory answered a question, whether the rules are sure and whether to ask a human is a decision. An exploratory session that acts, looks and acts again for minutes is a long loop. On one laptop: a pipeline runner and Playwright Test for jobs, plain Python for decisions, and LangGraph only for the exploration loop.

// sketch
def triage(failure, run) -> Verdict | None:
    """Returns a verdict, or None after queuing a review item."""
    if hit := memory.fresh_human_verdict(failure.signature):            # (a) memory
        return hit
    rule = rules.classify(failure)                                       # (b) rules
    if rule and rule.confidence >= RULES_GATE:
        return memory.claim(failure, rule)
    votes = memory.labelled_neighbours(failure, k=K, min_sim=MIN_SIM)    # (b) neighbours
    if votes.unanimous and len(votes) >= K:
        return memory.claim(failure, Verdict(votes.label, votes.share, "knn"))
    p = llm.classify(failure, tier="small") if run.budget.allows_call() else None  # (c)
    score = calibrate(rule, votes, p)                                    # fitted on the benchmark
    if score.confidence >= MODEL_GATE:
        return memory.claim(failure, score.verdict)                      # (d) write back
    review.enqueue(kind="triage", node=failure.signature_node,
                   suggestion=score, evidence_dir=failure.evidence_dir)
    return None

# testomation review → for each open review_item
def decide(item, decision):
    memory.claim(item.node, Verdict(decision, 1.0, "human"), basis=item.basis)
    memory.human_decision(item, decision)
    traces.score(item.trace_id, name="triage", value=decision)
    apply_verdict(item.node, decision)        # same function the triage stage uses
    review.close(item, decision)

Evaluation

Without ground truth there's no way to tell whether a new prompt, threshold or model made Testomation better or worse. Review-queue scores help, but they only exist once humans have reviewed things. A seeded-bug benchmark works from day one.

// the benchmark
  • Target app — one small but realistic web app (auth, forms, CRUD, lists) run locally with a seeded database: Conduit, the RealWorld demo app (React + Express + Postgres), vendored into the repo so bugs can be planted in it. It resets to its seed in about two seconds.
  • Hand-planted bugs — about twenty across categories: broken flows, missing validation, 5xx responses, console errors, layout breaks, accessibility violations, an intentionally flaky element, and harmless noise that must not be reported.
  • Mutation bugs — a mutation-testing tool such as Stryker adds many small automatic bugs. Only detectable mutants count — ones a hand-written reference suite kills — since the rest change nothing a user could see.
  • Toggles — every bug can be switched on or off, so the same app runs clean or bugged.
  • Replay bundles new — the recorded evidence of each bug's failure, with its expected label, so the analyzer can be re-scored without running the app.

// how it's used
  • testomation bench (full) and testomation bench --replay — results go to bench/results/ and, from phase 3, to Langfuse dataset runs.
  • Gate every change — analyzer changes on the replay tier; generation, planning and model changes on the full tier.
  • Calibrate thresholds — the rules gate, the neighbour vote, the model gate and how the three signals combine are fitted on the benchmark's precision and recall, then refined with review-queue scores.
  • Pick models — the model-tier candidates in §10 compete on the benchmark, not on reputation — including whether the large tier earns a place at all.
  • Hold some bugs out — a held-out set of seeded bugs (and their replay bundles) that prompts are never tuned against shows whether changes really improve detection or just fit the benchmark.

Design risks worth building around

Self-healing can hide real bugs

A tool that quietly swaps in a new target when one breaks and re-runs isn't the same as understanding why it broke. If a button moved because a layout regressed, silently "healing" the test buries the exact bug it existed to catch. Approved specs never self-heal: any change is a drift signal and a review item, and repairs to drafts can't touch assertions.

Agent runs are slow and non-deterministic

Great for exploratory bug-hunting, bad for a regression gate that needs to be fast and repeatable. Keep spec execution and agentic exploration as two distinct modes rather than asking one agent to do both jobs well.

Small local models are weaker

A 4–8B model will misjudge things a frontier model wouldn't. Measure that in a spike before building anything, keep their jobs narrow, make them fill schemas instead of writing code, put deterministic tools first, derive confidence from label probabilities and labelled neighbours rather than self-report, and gate every prompt or model change on the benchmark.

Memory can learn the wrong lesson

If the Analyzer once wrongly decides a 500 error is noise and saves that as a signature, it will ignore that bug on every future run. It's the same failure mode as self-healing, made permanent. Suppressions inferred by a model — from the LLM or the neighbour vote — must stay in the review queue until a human confirms them.

Stale memory looks like fresh knowledge

A target or flow that was correct last month may not be today. Every claim records the file and page-structure hashes it was based on and counts only while they still match; stale nodes and claims are hints, not answers.

Shared app state makes tests lie

If tests share accounts or leftover data, failures depend on run order and every flake signal is noise. Restore the seeded database before each run and give each test its own synthetic user.

The laptop becomes the bottleneck

Langfuse, a loaded model, the target app and several browsers compete for 16 GB of RAM and 4 GB of VRAM. Swapping makes tests time out and look flaky. Use one model by default, unload it while specs run, batch repair rounds, start Langfuse only in phase 3, and record machine load with each run.

A compute budget can quietly cost coverage

A tight budget that routes everything to the review queue just moves the work to humans. Watch review-queue size next to model calls and time; if one drops while the other climbs, the budget is set wrong.

Two orchestrators can blur into one

If LangGraph starts handling parallel runs and retries, or the pipeline runner starts encoding agent decisions, you get two half-overlapping systems and state that lives in both. Keep the line sharp: the runner and Playwright own jobs, agent code owns decisions, and LangGraph runs only the exploration loop.

Page content can steer the modelnew

Aria snapshots and error text from the app go into prompts, and a page — or user-generated content on it — could contain text that reads like an instruction ("this error is expected"). Page text is passed as delimited data, outputs are schema-constrained enums, nothing model-written runs, model-inferred noise never suppresses without a human, and specs and exploration stay on the target origin.

A small benchmark gives noisy numbersnew

With about twenty bugs, one bug is five points of recall, and the models are stochastic — a "regression" may just be chance. Detectable mutants add volume, every benchmark repeats three times with ranges, and a held-out set guards against tuning to the test.

Infrastructure before proofnew

Months of plumbing could come before discovering that local models can't do the core job. A throwaway feasibility spike with measured exit targets comes first (§15).

Building what already existsnew

Playwright's own Planner, Generator and Healer agents overlap planning and generation. Testomation's differences are kept explicit: JSON specs, no self-healing, memory across runs, bug-vs-noise triage, local models, and a benchmark (§00).

Build order

SPIKE new

Prove the models

One to two throwaway weeks: Conduit, a minimal spec runner, Ollama and a script — no Postgres, Langfuse, LangGraph or memory. Measure how many generated specs pass on the clean app (small vs large tier), how well one-call triage with logprobs works on about twenty captured failures, and peak RAM with a model and two workers. Confirm structured output and logprobs through the client. The result is a short report with numbers; see §15 for the targets.

PHASE 0

Set the stage

Compose stack (Postgres + pgvector — Langfuse waits for phase 3), native Ollama with the model the spike picked, a target app with a seeded database and reset, and the seeded-bug catalogue with toggles, detectable mutants and replay bundles. testomation bench can already score a hand-written suite, three runs with ranges.

PHASE 1

Prove the plumbing

The spec schema (one source, generated types) and the Playwright spec runner with fixtures, helper registry and origin guard, running hand-written specs and capturing evidence. Results are ingested as result rows, and the same ingest reads external Playwright reports. Create the memory schema now — typed tables, claims, basis hashes — with specs and runs as its first nodes and a static route → file map giving the first touches edges. Stage spans go to an OpenTelemetry file. No model calls yet.

PHASE 2

Tell bugs from noise — rules only

The analyzer's deterministic half: assertions, status codes, console allowlist, axe, screenshot diffs, flake history, dedup by error hash — for spec-runner results and imported Playwright suites alike. It writes rule claims, noise signatures and a local report. Its scores on both benchmark tiers become the baseline every model-based feature has to beat.

PHASE 3

Generate specs from plain English

Langfuse comes up. Test gen with the small model: described flow → JSON spec under constrained decoding, up to three batched repair rounds with the model unloaded while drafts run, and drafts promoted with testomation approve. The large tier is tried on the benchmark and kept only if it earns its place.

PHASE 4

Plan the coverage

A planner built as crawler + parser + aria snapshots first, with the small model naming and ranking flows and inferring business rules. It populates Page, Component, Element, Flow and ApiEndpoint nodes with aria basis hashes, and re-plans only pages whose basis changed.

PHASE 5

Put the model in the loop

The analyzer cascade in plain Python: memory → rules → labelled neighbours → small model with logprobs → calibrated gate → review_item. testomation review decides items; decisions become human claims, trace scores and new labelled neighbours. Gates, the neighbour vote, the score combination and the budget are calibrated on the benchmark.

PHASE 6

Go exploratory

Fuzzing and coverage-guided crawling with invariant checks first, then a text-based exploratory agent over aria snapshots — the one LangGraph loop, checkpointed, choosing spec steps on the target origin and stopping when budget or new states run out — an optional small vision model, plus flaky-test quarantine and visual baselines.

LATER

Platformize

CI/CD plugins, dashboard and trend analytics (read from the memory graph and Langfuse), GitHub Issues / Jira / Slack, production synthetic monitoring, RBAC, multi-project UI, the plugin architecture, WebKit through the Playwright container, test selection once the full suite gets slow — and Temporal, if Testomation ever outgrows one machine.

Design roadmap

§14 says what gets built in which phase. This section says what has to be designed and decided before each phase starts, what each design step produces, and how you know it's done. The rule: design one step ahead of the build, not the whole thing up front. Steps 1–3 come before any product code; after that, each step is finished just before its phase starts.

// how design decisions are made
  • Measure before deciding — anything that depends on model quality (tiers, thresholds, budget, prompts) is decided by the spike or the benchmark, not by argument.
  • Freeze contracts, not internals — the spec schema, file formats, table DDL and the llm client interface are versioned and changed deliberately; the code behind them changes freely.
  • Write it down in order — the decisions log first, then every doc that references it, then this brief.
  • Every step has an exit gate — a step is done when its gate passes, not when the document looks complete.
